# Tenant export and the erasure register

A site (one tenant, ADR 017) leaves an installation as a directory or a `.tar` and arrives in another one with the same data, the same ids and the same files (PR #32, ADR 002 rule 5). The same archive is the way back after a site was lost on this installation. Export is never gated by an entitlement or a suspension (ADR 015 rule 7). The commands are in [`../self-hosting.md`](../self-hosting.md#export); the code is [`packages/db/src/portability/export.ts`](../../packages/db/src/portability/export.ts).

## In short

**Export and erasure** (PR #32, migration 0019). A tenant leaves an installation as an archive of its rows, read as `mycel_app` in its own context, plus its media files, and arrives in another through one transaction (`packages/db/src/portability/export.ts` and `import.ts`, `mycel export|import`, `docs/reference/export.md`); every table of the schema is placed in `TABLES` there, so a new one is in or out of the export by decision, never by accident. Erasure is a permanent register (`ctx.erasures.register`) plus an idempotent apply that only the worker and the CLI can run, as the tenant-bound role `mycel_erasure`, and that a restore runs again. A registration is completed once a backup holds it: the backup login records that in `erasure_backups` (PR #39, migration 0021) and `ctx.erasures.status()` reads it.

## Format

```
manifest.json
tables/<table>.ndjson     one line per row
media/tenants/<id>/...    every file in the blob store under the tenant's prefix
```

`manifest.json` holds `format` (`mycel-tenant-export/1`), `schemaVersion` (the last migration applied to the exporting database, such as `0019_erasures`), `mycelVersion`, `exportedAt`, the tenant (`id`, `slug`, `name`, `locales`, `defaultLocale`, the stored `entitlements` document and `status`), and per table and per media file the file name, the number of rows or bytes and a sha256. Per table it also lists the columns, so an import into a newer schema writes exactly those and lets later columns take their defaults. A later column that is `not null` without a default is derived on import the way its migration backfilled it (`DERIVED` in `packages/db/src/portability/export.ts`): `form_submissions.list` and `consent_text_version` (0020) come from the form's definition. Such an import reports a fingerprint difference for that table, by design.

A row is Postgres's own `to_jsonb(row)`: timestamps with microseconds and their offset, `jsonb` as JSON, arrays as arrays, bigints as numbers. Lines are sorted by their text, so two exports of the same data are byte for byte equal. Ids are UUIDv7 and travel unchanged; that is what lets two installations exchange sites without collisions (ADR 002).

## What travels, in this order

`tenant_hostnames`, `forms`, `form_submissions`, `supporters`, `supporter_admissions`, `events`, `people`, `person_groups`, `person_group_members`, `sections`, `patterns`, `media`, `media_usages`, `content_items`, `content_revisions`, `content_bulk_plans`, `content_bulk_plan_items`, `content_bulk_runs`, `content_bulk_effects`, `content_item_locales`, `content_block_refs`, `content_search`, `campaigns`, `campaign_participations`, `tenant_memberships`, `audit_log`, `erasures`, `person_erasures`. A table's foreign keys point at tables earlier in the list. The export reads them as `mycel_app` in the tenant's context, in one repeatable-read snapshot: it holds exactly what row level security shows that tenant, and nothing of another.

**The files come after the tables, and the archive is complete or not written** (PR #38, ADR 019 rule 8). Every file of every media row that is live in the table snapshot is in the archive (the keys `mediaKeys` in `packages/core/src/media/model.ts` gives that row). A media item deleted while the export runs still has its files, because `media.delete` removes them only 24 hours later (`MEDIA_PURGE_DELAY_MS`, [`media.md`](media.md#usages-and-deleting)). If a needed file is missing anyway, or the files are read more than 12 hours (half that delay) after the snapshot, the export fails with the media ids and leaves no directory and no `.tar` behind; a directory given as `--out` must be empty or absent. Files under the tenant's prefix without a live row travel too: a variant the register lost, or an upload that committed after the snapshot. The latter has no row in the archive, so after an import the orphan sweep removes it a day later.

Every table of the schema has its place in `TABLES` in `packages/db/src/portability/export.ts`: `export`, `operational` or `platform`. A migration that adds a table does not compile until it has one, and `export.conformance.test.ts` fails when the live catalog has a table with a `tenant_id` that is not placed. A new tenant table is therefore part of the export from the pull request that adds it.

Two tables change on the way:

- **Memberships** travel as the operator's address instead of this installation's operator id. Import invites that address as a pending operator, as `mycel setup` does; the person logs in again on the new installation. Only the capabilities this version knows travel: a membership from a newer installation loses the ones this one cannot grant, and a membership left with none (or with an address that is not one) is skipped and counted in the report. These rules, the manifest checks and the hostname rule below are in `packages/core/src/tenants/portability.ts`.
- **Hostnames**: the platform hostname is the installation's own (`<slug>.<PLATFORM_DOMAIN>`), so the importing side makes a new one and skips the exported one. A custom hostname arrives unverified and not primary: DNS may point elsewhere, and the daily check or Check DNS in the admin verifies it once it answers here.

## What does not travel

| Not exported                                                    | Why                                                                                                  |
| --------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------- |
| `outbox`, `jobs`, `mail_sends`, `rate_limits`, `login_attempts` | Work in progress and counters of this installation, not the site's data; the new one starts its own. |
| `erasure_backups`                                               | Which of this installation's snapshots hold a registration; an import starts unsecured.              |
| `tenant_exports`                                                | Earlier archives of this site (below); an archive in an archive would grow with every export.        |
| `operators`                                                     | Accounts of people who log in here; a membership carries the address instead.                        |
| The `tenants` row                                               | It is in the manifest; import creates the tenant through the platform path, with its audit row.      |
| `api_keys`                                                      | Credentials of this installation. A hash that travels works here; create new keys after an import.   |

## Import

`mycel import <path> [--slug <slug>]` checks before it writes anything: that every entry is a regular file or a directory (a link is refused, whatever its digest), the format, every file against its sha256 and row count, that the export's schema is not newer than this database (`0020_x` into a database at `0019_erasures` is refused; older is fine, `migrate` already brought the database past it), and that neither the slug nor the tenant id exists here. Then it writes everything in one transaction: the event partitions for the exported months, the tenant as `mycel_platform` (audit row `platform.tenant.import`), every table as `mycel_app` in the tenant's context (row level security refuses a row of any other tenant), and the media files last. A failure anywhere rolls the rows back and removes the files already written: a failed import leaves no half site. An archive from before migration 0055 has no `content_search`; the import builds the site search index from the imported publication rows in the same transaction and reports `content_search: not in the export (older schema), rebuilt, N rows`.

Afterwards it reads the site back the way export does and compares every table with the manifest. Equal except by design: the platform hostname, the verification of custom hostnames, and the one audit row of the import itself. It prints per table how many rows it imported and skipped, and exits non-zero on any other difference.

An archive from before API keys stopped travelling still imports: its `api_keys` file is checked against the manifest, not read into the database, and the report counts it.

## Self-service export

A site administrator (`tenant:admin`) asks for the same archive in the admin, at `/admin/<site>/export`, without the hoster (PR #40, ADR 015 rule 7). It works while the site is suspended; besides `supporter.erase` it is the only command that does (both are data-subject rights, ADR 015 rule 7 as amended).

- **Ask**: the command `tenant.export.create` (effect `export`, requires `tenant:admin`: the archive holds members and the audit log, more than `supporters:export` covers). It writes a `queued` row in `tenant_exports` and plans the job `tenant.export` in one transaction. While one export of the site is queued or running, a second ask returns that one (a partial unique index, so a double click or an agent in a loop cannot have ten archives built). `tenant.export.list` shows the archives with status, who asked, size, sha256 and until when it can be downloaded; never where the file is. Both are HTTP routes and MCP tools; downloading is not.
- **Build**: the worker runs `exportTenant`, the code behind `mycel export`, into a temporary directory of its own and streams the `.tar` to the blob store under `exports/<tenant id>/<export id>.tar`. Not under `tenants/<id>/`: export reads that prefix as media, and the orphan sweep would delete the archive a day later. A run renews its job lease and the row's `heartbeat_at` every minute, so an export longer than the five-minute lease is not started twice; a run that finds a heartbeat older than a lease (its worker died) starts over. A failure marks the row `failed` with a scrubbed error and is not retried: the administrator asks again.
- **Download**: `GET /admin/<site>/export/<id>?exp=&sig=`, on the admin host only. It needs the operator's session, a membership of that site with `tenant:admin` at the moment of downloading (a member removed after asking gets nothing), a `ready` archive whose time has not run out, and a link signed for five minutes over `export:<tenant id>:<export id>:<exp>` (the admin page makes a fresh one on each load). Every refusal is the same 404. The response is `application/x-tar` as an attachment (`<slug>-<date>.tar`), `Cache-Control: private, no-store`, streamed from the store. Every download writes an audit row `tenant.export.download` with effect `export` and the export id as subject.
- **Lifetime**: an archive can be downloaded for `EXPORT_RETENTION_DAYS` elapsed 24-hour periods (7 by default) after it was finished, including across daylight-saving changes. The daily platform job `tenant.export.expire` works per tenant as `mycel_app`: it expires ready archives past their time or without their file (after a restore), deletes the files of expired and failed ones, and removes rows older than a year. Archives do not count towards `media.storage_max_bytes`: a limit never stands in the way of leaving.
- **Backups** leave `exports/` out (`rclone sync --exclude 'exports/**'` in `docker/backup/backup.sh`; the restore drill checks the snapshot). An archive is a derived copy with its own retention, and a snapshot would keep it beyond both that and an erasure. After a restore the rows come back without their files; the daily job marks them expired and the administrator asks for a new one.

## Readmission evidence

`supporter_lifecycles` travels unchanged with tenant data and full backups (migration 0046, ADR 032). Its id, address hash, first submission id and server time prove explicit readmission after a registration; the pinned submission and event/projection identity determine which copies belong to it. Import never invents lifecycle evidence for old archives. Their rows are imported losslessly, and an applicable registration still erases their unproven copies. The register remains permanent and a second lifecycle is independently erasable. Apply serialises with admission and ingest on the same address hash, and retains only proven current copies after the latest cutoff; equal timestamps belong to erasure.

## Erasure register

Erasing a supporter (ADR 003 rule 5, ADR 019 rule 8) has two halves, so that the second can run again after a restore:

- **Register** (`ctx.erasures.register(supporterId, email)`, as `mycel_app`, through `supporter.erase`, [supporters.md](supporters.md#erasure)): one permanent row in `erasures` with the tenant, the supporter id, `erased_at`, the actor, and `email_hash`, the hex sha256 of `<tenant id>\n<normalised address>` (`emailKey(..., 'erasure')`). Never the address. Nobody may update or delete a registration (migration 0019).
- **Apply** (`ctx.erasures.apply()`: the worker's `supporter.erase` and daily `erasures.apply` jobs, and `mycel erasures apply [--tenant <slug>]`): for every locked registration of the tenant, find the addresses (the supporter's projection and events by id, and any projection or submission value whose hash is registered), then, except for proven current lifecycle copies (above): events and the projection become tombstones (`<supporter id>@erased.invalid`, empty props, empty lists; type and time stay, so every count still adds up); submissions that contain the address are deleted; outbox events that carry it are scrubbed, and the mail intents and `mail.reconcile` jobs of those events are deleted; jobs whose payload carries it are deleted; the admission seat of a signup that was never ingested is deleted under its own key (migration 0032). A recipient cooldown bucket in `rate_limits` stays: a hash that lives a day at most is no copy (ADR 019 rule 8), and wiping it would reopen the cooldown. Every key derived from an address comes from core `emailKey`. Export archives (above) that may hold a registered person are expired: every `ready` or `running` one when the apply changed anything, and every one asked for before the newest registration; their error says "deleted after an erasure" and nothing about whom. `mycel erasures apply` deletes their files right after, the daily `tenant.export.expire` otherwise. The audit log stays: it holds pseudonymous ids and keyed hashes only ([`audit.md`](audit.md)). Address discovery and row selection use core `normalizeEmail` and `emailKey`, including on restored rows, rather than SQL case folding or trimming. Structured JSON is inspected after decoding (including keys); free text matches a whole address bounded by mailbox characters, so `ann@example.org` does not select `joann@example.org` or `ann@example.org.evil`. A final sentence period is punctuation. Apply is idempotent and prints how many rows it changed; a second run changes none.

Apply needs rights `mycel_app` does not have (the event log is append-only for it), so it enters the role `mycel_erasure`, which may do exactly the above and only on the current tenant's rows. Only the schema owner may enter it: the worker and the CLI apply; a web request registers. The use case `supporters.erase` that registers and the projection that folds tombstones are the next step (TODO, phase 2).

**Secured** (PR #39, migration 0021): a registration lives in the database until a backup holds it, and a restore after losing the server would bring the person back with no register to say otherwise. So the backup records it: after a successful `restic backup`, the full run and the `erasures` run every 15 minutes insert one row per registration their snapshot holds into `erasure_backups` (tenant, supporter id, the restic snapshot id, `secured_at`); the backup login may insert there and write nowhere else. `ctx.erasures.status()` returns per tenant `registered`, `secured` and `oldestUnsecuredAt`; `mycel erasures status` prints it per site and exits with 1 when a registration has waited over an hour; `ops.status.get` shows the same as a warning. **A registration is a completed erasure only when it is secured.** The use case `supporters.erase` (phase 2) reports "done" on that, never on `register` alone. `erasure_backups` does not travel with an export: another installation's snapshots say nothing about this one's, so an imported registration starts unsecured.

**After a restore** of a snapshot, people erased since it was taken are back. `restore erasures latest` loads the register of the newest erasures snapshot and of the newest full snapshot into the restored database and `mycel erasures apply` erases them again, before the sites open ([`../self-hosting.md`](../self-hosting.md#restore), step 4). A snapshot list or register restic cannot read stops that step with an error instead of counting as no register. The restore drill rehearses this, including an erasure only the erasures snapshot holds and a restic that cannot list the erasures snapshots, and fails if an address is still in any table, any object key or `pg_dump --data-only`.

## Person erasure

Erasing a person of the people register ([ADR 034](../adr/034-person-erasure.md), migration 0050) uses the same two halves, by explicit person id; a person id is never derived from a supporter, an address, a name or a credit text.

- **Register** (`content.person.erase`, effect `erase`, capability `supporters:erase`, accepted while the site is suspended): one permanent row per person id in `person_erasures` (tenant, person id, `erased_at`, the actor; no name, no address). A request that names an id of neither the people register nor this register is refused whole and appends nothing; a registered id is a no-op. It plans a `person.erase` job ([jobs.md](jobs.md)). The result lists per id whether apply has run, and always says what an id cannot reach: names typed in text and the pixels of images.
- **Apply** (the person phase of `ctx.erasures.apply()`, in the same per-tenant run as the supporter phase, `packages/db/src/people/erasures.ts`): deletes the `people` row and its `person_group_members`; the ids in documents, revisions, patterns, plans, `content_block_refs` and media credits stay as references to nobody, and the slug is free. Then the one in-place change ADR 034 allows: in every revision (trashed items included), pattern, plan slot (`selection` and `preview`, change values at a credit's `photographer` path included) and media credit, a credit whose `photographerPersonId` is registered gets `photographer: null`. Ids, structure and revision ids stay. The scrub is core's (`scrubErasedCredits` in `packages/core/src/content/people/erasure.ts`); `mycel_erasure` has update on only those JSON columns, and `mycel_app` still has none on revisions or plans. Archives asked for before the newest person registration expire, as for supporters. Idempotent: a second apply changes nothing.
- **Invariant at rest**: every write that stores a credit (save, block operation, restore, bulk apply and undo, a new item, a pattern, a bulk plan, `media.update`) stores `photographer: null` beside a registered id after any merge, whatever the caller sent. Such writes take the tenant's person-erasure lock shared and a registration takes it exclusively, so a write that commits after the registration reads it. A registered id passes the reference check of save, publish, schedule, the scheduled run and bulk apply and undo (rule 7); an id in neither register is still refused, and `media.upload` refuses a registered id on a new file. The public site never falls back to the free text of a credit whose person is absent.
- **Restore and import**: the register travels in the export and in the erasures snapshot (`person-erasures.copy` beside `erasures.copy`, read back by `restore erasures latest`), and `mycel erasures apply` erases the person again before the site is back.

## Content bulk archive inventory

`content_bulk_plans` holds the authenticated historical actor (the same attribution shape as a revision). `content_bulk_plan_items` holds requested document input, a validated candidate, structured differences and the observed publication pointers. These are editorial archive copies, not supporter projections or a new PII cache; no supporter events, submissions or mail recipients are copied into them. They are exported and imported after content revisions with composite tenant/item references intact. They share the revision archive's lifetime; there is no automatic purge. Supporter erasure does not search arbitrary editorial prose or revision attribution today, and does not search these copies either. `content_bulk_runs` holds the undo barrier; `content_bulk_effects` holds phase receipts with historical actor, item snapshots and composite before/after revision pointers, not additional document copies. Both travel in exports after the plans and revisions. Any editorial archive retention or erasure policy must include all four tables and their actor/input/candidate/diff fields alongside revisions (ADR 028).

Since migration 0041, legacy archives containing `authors` import those rows into `people`, preserving ids and internal email. Newly added columns retain their defaults; groups and ordered memberships travel in new archives.
