# Running the frontend quality measurements

The runner uses Lighthouse 13.5.0 directly as a replaceable Apache-2.0 development dependency, with chrome-launcher 1.2.1. LHCI was rejected after its dependency audit; the direct runner was explicitly approved. The application, domain and browser bundles do not import either tool. There is no Lighthouse server, telemetry or public report upload.

## Local measurement

Use a production build, the normal local database configuration in `.env`, installed Playwright Chromium, Caddy and OpenSSL. Commit the tree before measuring: the runner refuses dirty source and never overwrites an output directory. Do not run other builds or browsers on that runner while collecting samples.

```sh
npm ci
npx playwright install chromium
npm run build
npm run quality
npm run quality -- --scope=full --locale=en --profile=desktop --cache=warm
npm run quality -- --route=article --cache=cold
```

`quality` reuses the end-to-end seed, mock IdP, API, worker, database lock and schema preflight. The web process receives application/authentication database credentials only. The fixture hash covers the original manifest bytes and `scripts/e2e/e2e.mjs`; corpus version is `43a-v4` (campaign, article and `grid-information-v1`); retained `43a-v3` runs keep their original two-page coverage. Item ids come from the seeded API, and authenticated measurement uses the synthetic end-to-end operator. The operator's cookie is scoped to `/admin` on localhost through CDP, never sent as a global request header or persisted in a summary.

The default set measures all three public pages in Dutch, mobile, with five sequential samples per page. `--scope=full` includes the populated admin list, native editor and enhanced writer; `--scope=admin` measures only those three. Locales are `nl` and `en`; profiles are the pinned Lighthouse simulated mobile and desktop presets. Browser selection follows the exact Playwright version/revision in `package-lock.json`. Each measured sample starts a fresh Chromium process. `fresh` uses empty browser storage/cache; `warm` performs one unmeasured navigation in that fresh process before the measured navigation. `cold` additionally restarts the web process before every sample; its database and proxy remain warm. No mode claims a cold host, database or deployment. `--diagnostic` permits one additional five-sample batch for inconclusive or performance-only failures; both batches remain in the result.

Caddy provides HTTPS and the production `encode zstd gzip` and operational-route exclusions. TLS uses one ephemeral localhost certificate trusted by its SPKI only, with no general browser certificate bypass. Application CSP, cache headers and consent behaviour remain intact. The timed navigation supplies its own DOM identity artifact, response headers, request outcomes and errors. Every declared image URL, including lazy below-fold images, is checked after measurement. This validation does not alter Lighthouse timings. No login, missing image or wrong item can satisfy the evaluator.

Reports go to a unique `.scratch/quality/` directory, or `--out=<new-directory>`. Every sample has its original Lighthouse JSON/HTML, trace, network summary and identity metadata. The aggregate preserves raw category scores, metric values, spread, applicable audit ids and all batches. `summary.json` records the SHA, corpus hash/version, tool/browser/OS/runner settings, elapsed runner minutes, coverage gaps and repair proposals. A non-pass result exits nonzero. `--baseline=<summary.json>` adds diagnostic comparisons only when corpus, tools and runner settings agree and the predecessor passed. Absolute thresholds never change.

## CI and artifacts

The separate `Frontend quality` workflow builds once and reuses the build in isolated PostgreSQL/browser shards, each with a ten-minute deadline. Installation has a three-minute limit and measurement a six-minute limit, leaving artifact handling within the job budget. Each shard pulls the same digest-pinned Playwright Noble amd64 container, including browser libraries and fonts, instead of installing mutable host packages. The container uses the checked-out production build and lockfile dependencies, the setup-node installation mounted read-only and the checksum-verified Caddy binary mounted read-only. It runs as the runner user with an explicit environment list and host networking to its isolated PostgreSQL service; GitHub token environment variables are not forwarded to the measurement process. Every PR and main push runs the Dutch public corpus on mobile and desktop. Weekly Monday 05:17 UTC and manual dispatch use the same tested matrix: public nl/en, mobile/desktop, fresh/warm/cold, plus the three admin states in nl/en on mobile/desktop. An unmapped change still gets the default measurement.

CI pins Node 22.22.0, Playwright 1.64.1 Noble amd64 at digest `sha256:d65108d1a8095d8b0c4a5e32bf1807a40a5ce90ff0c78473e1116b1c243235e8`, Lighthouse 13.5.0, lockfile Chromium and Caddy 2.10.2 with its archive checksum. The source-bound runner identity is the immutable container digest. The container shares the host kernel, but independent GitHub hosts may roll kernels and host images separately. Cross-shard identity binds the source-pinned container digest and every actual browser/tool version (Node, Lighthouse, Playwright, Chromium and Caddy). Kernel releases and host-image builds are individually syntax-validated and retained per shard for diagnosis, not required to match. Each summary retains the actual rolling GitHub host image, kernel, Chromium, CPU and runtime versions. Host images no longer supply browser libraries or fonts. Kernel/CPU differences remain a measurement limitation visible beside each sample batch; the container does not pin a VM. Historical host measurements keep their original strict GitHub-image comparison; they cannot fill a container matrix or become its baseline. Updating Playwright requires a matching reviewed image digest. This establishes a consistent userspace, not a pinned VM or identical CPU hardware. Local results are a separate runner profile. Passing summaries also get a baseline artifact name. The workflow retrieves the latest successful main baseline for the cell profile; incompatible corpus/tool/runner settings explicitly produce no comparable baseline. Failed observation runs cannot replace the successful baseline history. Older successful reports remain in artifact history.

Raw public reports and encrypted admin originals are retained for 30 days; sanitized summaries for 90 days. Artifact upload and encryption run after failures too. Authenticated reports are archived with OpenSSL CMS to the public recipient certificate in `scripts/quality/artifact-recipient.pem`; CI has no decryption key. The operator keeps the matching private key outside git and CI. To inspect an authenticated archive:

```sh
openssl cms -decrypt -binary -inform DER -in private.tar.gz.cms -inkey /path/to/operator-private-key.pem -out private.tar.gz
tar -xzf private.tar.gz
```

Keep the operator key in controlled storage. Replace the public recipient in a reviewed tooling PR if the private key is lost or rotated; retain older private keys while their artifacts are retained. Plaintext admin originals remain locally in the ignored output directory for inspection; GitHub uploads only the encrypted archive and sanitized aggregate. The output directory and temporary key directory are owner-readable only.

## Calibration and enforcement

The [stable check and protection runbook](frontend-quality-enforcement.md) defines matrix validation, the fixed UTC boundary, reviewed early activation, the proposed protection request and the independent activation/negative-proof procedure. Configuration in git is not evidence that protection has been applied.

The first CI result was on 2026-10-26. The ten-working-day observation window ends on 2026-11-06. The deadline in `scripts/quality/enforcement.json` is the single source for when non-pass measurements block; `gate.mjs` and `status.mjs` read it. **Decision, 2026-10-27:** the original 2026-11-09 deadline is suspended (`"deadline": null`, meaning not enforced until a date is set) until the product matrix has been fully green once; after that a dev session proposes a new date in a reviewed change. While suspended, `fail`, `inconclusive` and `not-measured` are still reported and broken evidence still fails the check; only the blocking consequence of a measured non-pass is off. Dev owns enforcement under frontend-quality step C. Enable blocking earlier once two independent complete batches on one candidate SHA meet the contract and the negative evaluator fixtures pass. Existing verify, security and accessibility gates remain blocking throughout. Reports always retain their real `pass`, `fail`, `inconclusive` or `not-measured` state during observation.

Branch protection is a separate delivery criterion. On 2026-10-26 the GitHub branch-protection endpoint returned “Branch not protected” for main. Since 2026-10-28 `main` is protected and the measurement statuses are required checks, both in the branch protection and in the merge-queue ruleset ([enforcement runbook](frontend-quality-enforcement.md)); what stays open is keeping the admin/weekly evidence in the release decision. A successful observation job is not proof that the measured cells pass. Missing summaries fail the status step even during calibration; disabled/missed schedules are inspected by the read-only history consumer below. The first scheduled event after merge remains unobserved until it actually occurs; manual dispatch exercises the same matrix but cannot prove a scheduler fired.

## Coverage and repair boundaries

The summary explicitly records the dynamic POST/iframe preview as unmeasured until a versioned state contract exists. A bare preview GET is an empty shell. The demanding theme in `43a-v4` is simulated, so it cannot establish a persisted tenant-theme measurement; that fixture belongs to the theme work. SiteChrome is now rendered on the public routes; its old planned manifest entry is superseded by those real measurements without changing the content-owned corpus. Future collections, restricted reads, conditional forms and managed embeds retain their implementation dependencies.

Manual keyboard/screen-reader, real browser zoom, hero contrast and field data keep the release scenarios and limits in [the quality contract](../architecture/frontend-quality.md). These automated runs do not establish WCAG conformance or real-user INP. Repairs go into the existing component, renderer, security or representation suites; the runner emits proposals and never rewrites private planning. A score failure does not authorize lowering thresholds, suppressing assets, changing security policy or fixing product code in the measurement PR.

## Consuming history and checking missed schedules

The retained evidence of one run is validated by `scripts/quality/evidence.mjs`, which the required `frontend-quality` job imports. It reads the original v1 summaries without decrypting admin evidence, validates the measured source contract, and retains every run/attempt/batch. Source contracts come from corpus, seed, lockfile, workflow and matrix bytes at the measured commit. A PR head and its measured merge commit are separate fields. Unsupported future corpus/matrix versions are missing evidence until a reviewed adapter supports them. Duplicate artifacts/cells, mismatched provenance, unavailable/corrupt reports and interrupted runs cannot pass. No latest/best-run selection occurs. Coverage gaps and repair proposals carry what the measured report said about them (`sourceAddress`, `sourceOwner`, `dependency`, claims) as bounded tokens, plus the cause class and whether it touches a security boundary; the validator does not decide where a cause is repaired.

Reading the Actions history across runs, the weekly schedule clock, the daily watchdog, routing of causes to planning items and owners, and the factory report that derives process metrics from the same history are the platform owner's process. Since 2026-10-27 they live outside this repository, in the owner's private tooling, which imports this validator from a product checkout. Until actual weekly and watchdog firings are observed, the owner runs that tooling locally with the current UTC clock and records the date and outcome there. Both GitHub schedules can fail, so this is not independent external monitoring.
