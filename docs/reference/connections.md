# Managed connections

A managed connection is a tenant's registered link to an external service: an inventory entry, an encrypted credential and a durable intent engine that delivers work to it. The only transport today is the generic signed webhook ([managed-webhooks.md](managed-webhooks.md)), and the only source it delivers is an explicitly requested synthetic test; no form, supporter or other real data leaves the installation through a connection yet. A newly registered connection starts paused and without a credential. Tenant administrators manage connections at `/admin/<tenant>/connections`.

Each connection belongs to one tenant and names its provider, external account, external data owner, maintainer, purpose, direction, authority for data and consent, consent scopes, mapped forms, approved destination, contract version and adapter version. The connection version increments on every metadata, state or credential change. Later transfers must pin that version and refuse a changed destination or credential. Disconnect is terminal and deletes the stored credential. A disconnected connection retains redacted metadata for the inventory and export.

`connections:read` sees metadata and whether reconnect is required. `connections:configure` creates, edits, pauses, resumes and disconnects. `connections:credentials` replaces the secret. A tenant administrator holds all three through the existing `tenant:admin` override; an API key or agent receives only its granted capabilities. Every command is audited through the shared invoker. The credential itself appears in no output, audit row, error or log. API and MCP expose the same registered use cases.

The installation encrypts credentials with AES-256-GCM under `CONNECTION_CREDENTIAL_KEY`, which must be 32 random bytes encoded as 64 hex characters. Authentication binds the ciphertext to tenant, connection id and credential version. The key is separate from `AUDIT_HASH_KEY`; preserve it with the installation's secret backup. It is required for production startup and for credential replacement in development. Replacing a credential increments both connection and credential versions. The credential table is operational and excluded from tenant export. Connection metadata is exportable; after import, `credentialStatus` reads `reconnect-required` until a tenant operator replaces the secret. A restored installation must have the original key to use existing credentials. Rotate the key only through a planned re-encryption migration.

Both tables have forced tenant RLS. A suspended tenant may read its inventory but cannot change it, following the shared invoker rule. A webhook destination is checked when it is saved and again on every delivery: public HTTPS on port 443, a hostname rather than an IP literal, and a DNS answer that contains only public addresses (`checkedDestination` in `packages/api/src/webhook.ts`). The request is pinned to the checked address and follows no redirect. A connection does not authorize a transfer by itself.

## Durable intents

`planConnectionIntent` is an internal transaction boundary; the `connections.run` tenant job delivers what it plans. The worker requires explicit source and transport dependencies. The production composition (`packages/api/src/compose.ts`) installs the webhook transport and one source, `synthetic.test`, which `connections.test` (capability `connections:configure`) queues with synthetic data only; any other source fails closed. An action subscriber that delivers real data must call planning inside its own tenant transaction, with a UUID business id, connection version, source, mapping version, supporter id and consent scope. An identical business id on one connection returns the existing intent; a changed contract conflicts. Intent and job commit together. The provider key is a deterministic SHA-256 of tenant, connection and business id.

The worker commits an `unknown` intent and a unique lease token before calling transport. Another worker cannot claim it during its 60-second lease. After a crash or expired lease it reconciles instead of sending. Only the transport's proof of final business success closes the intent; an HTTP 2xx qualifies only where the receiver contract defines it as durable acceptance, as `mycel.webhook.v1` does. A proven `pre_send` failure can retry. Reconciliation may return `absent` only if no previous call can still perform the effect, including an in-flight call whose lease expired. An ordinary empty provider search without that guarantee is `unknown`. There is no exactly-once promise.

Every dispatch and reconciliation reloads tenant access, the connection state and pinned versions, the original operator membership or API key capabilities, the erasure register and confirmed list membership. A trusted system producer derives its authority from the installed source, not from a stored human capability snapshot. Sources must resolve the exact pinned mapping and current operation-specific authorization and suppression; an uninstalled source fails closed. Source preparation is followed by another generic guard and lease check. No provider payload or credential is stored in intents, jobs, attempts or status results. A source must not perform an external write during preparation. Real adapters must enforce their own bounded request timeout, destination checks and provider reconciliation guarantees before installation.

Dispatch admission is the final guard before the external call. Pause, disconnect, credential rotation, withdrawal or erasure committed before that guard prevents dispatch. A change after admission cannot recall an already admitted external call; reconciliation and external-copy handling must report its actual outcome. Every connection state change increments its version, so resuming does not silently repin old intents. A new business decision is needed for an obsolete contract.

The engine permits at most 60 claim attempts per tenant per minute. Dispatch and reconciliation share a five-attempt automatic budget, with exponential backoff from one minute to at most one hour. Unresolved work remains `unknown` when the budget is exhausted and requires targeted manual handling; it is never marked delivered or automatically resent. `connections.intent.get` exposes only ids, state, a closed failure class, attempt count and timestamps. `connections.intent.replay` requires `connections:replay`, audits the request, rechecks current generic guards and queues work without clearing uncertainty, leases or backoff. The worker rechecks the installed source as well. Replay cannot revive completed, blocked or exhausted work.

Migration 0025 adds `connection_intents` and append-only `connection_attempts`, both under forced tenant RLS. Both are operational and excluded from portable tenant exports: importing unfinished work into another installation could duplicate effects. Installation backups retain them for recovery. Erasure detaches the supporter id, invalidates the worker lease and preserves anonymous success or uncertainty; pending work becomes blocked. The remaining business id is an opaque UUID, not an address or a submitted payload. This does not assert that an external copy was erased. Real-data sources, provider-specific suppression and reconciliation, and administration of external copies are not built yet. The generic webhook cannot reconcile: an ambiguous delivery stays `unknown` and is resolved by hand ([managed-webhooks.md](managed-webhooks.md#operator-response)).
