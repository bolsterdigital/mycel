# Managed connections

A managed connection is a tenant's registered link to an external service: an inventory entry, an encrypted credential and a durable intent engine that delivers work to it. The transports are the generic signed webhook ([managed-webhooks.md](managed-webhooks.md)) and Mailchimp Marketing API, with two installed sources: an explicitly requested synthetic test and the confirmed, versioned form feed. A newly registered connection starts paused and without a credential. Tenant administrators manage connections at `/admin/<tenant>/connections`.

Stored values are limited to what has an implementation: providers `webhook` and `mailchimp`, direction `outbound`, and the closed sets of intent states and failure classes in `packages/core/src/connections/`. Migrations 0028 and 0045 hold the database to the same sets. A new provider or direction arrives with its transport and its tests, not ahead of them.

Each connection belongs to one tenant and names its provider, external account, external data owner, maintainer, purpose, direction, authority for data and consent, consent scopes, mapped forms, approved destination, contract version and adapter version. The connection version increments on every metadata, state or credential change. Later transfers must pin that version and refuse a changed destination or credential. Disconnect is terminal and deletes the stored credential. A disconnected connection retains redacted metadata for the inventory and export.

`connections:read` sees metadata and whether reconnect is required. `connections:configure` creates, edits, pauses, resumes, disconnects and queues the synthetic test. `connections:credentials` replaces the secret. `connections:replay` requests a retry or resolves an unknown attempt. A tenant administrator holds all four through the existing `tenant:admin` override; an API key or agent receives only its granted capabilities. Every check, including the worker's recheck of the actor who queued an intent, goes through the one rule behind `can()` (`grants` in `packages/core/src/principal.ts`). Every command is audited through the shared invoker. The credential itself appears in no output, audit row, error or log. API and MCP expose the same registered use cases.

The installation encrypts credentials with AES-256-GCM under `CONNECTION_CREDENTIAL_KEY`, which must be 32 random bytes encoded as 64 hex characters. Authentication binds the ciphertext to tenant, connection id and credential version. The key is separate from `AUDIT_HASH_KEY`; preserve it with the installation's secret backup. It is required for production startup and for credential replacement in development. Replacing a credential increments both connection and credential versions. The credential table is operational and excluded from tenant export. Connection metadata is exportable; after import, `credentialStatus` reads `reconnect-required` until a tenant operator replaces the secret. A restored installation must have the original key to use existing credentials. Rotate the key only through a planned re-encryption migration.

Both tables have forced tenant RLS. A suspended tenant may read its inventory but cannot change it, following the shared invoker rule. A webhook destination is checked when it is saved (in the use case) and again on every delivery (in the transport): public HTTPS on port 443, a hostname rather than an IP literal, and a DNS answer that contains only public addresses. Both use `checkDestination` in `packages/core/src/connections/destination.ts` over the core DNS port (`DnsResolver.addresses`), so in-memory tests exercise the same rule. The request is pinned to the checked address and follows no redirect. A connection does not authorize a transfer by itself.

## Form feeds and future providers

[Form feeds](forms.md#versioned-connector-feeds) pin approved destination and mapping versions at submission, then plan this engine's intents after confirmed Mycel consent. The source rechecks current authorization, consent, erasure and the pinned submission before every external write. Only the webhook provider is currently installed. Provider-specific account setup, external confirmation ownership, suppression reconciliation and Mailchimp transport remain separate work.

## Durable intents

What runs today: `connection.test` (capability `connections:configure`) writes one synthetic intent and its `connections.run` job in the same transaction. The production composition (`packages/api/src/runtime/compose.ts`) installs the webhook transport and one source, `syntheticSource` from `packages/core/src/connections/synthetic.ts`, which also holds the only definition of what counts as synthetic. Any other source fails closed. `planConnectionIntent` is the transaction boundary a future real-data source will call (with a UUID business id, connection version, source, mapping version, supporter id and consent scope); nothing in production calls it yet. An identical business id on one connection returns the existing intent, a changed contract conflicts, and the provider key is a deterministic SHA-256 of tenant, connection and business id.

The worker commits an `unknown` intent and a unique lease token before calling transport. Another worker cannot claim it during its 60-second lease. Only the transport's proof of final business success closes the intent; an HTTP 2xx qualifies only where the receiver contract defines it as durable acceptance, as `mycel.webhook.v1` does. A proven `pre_send` failure can retry. There is no exactly-once promise.

After an ambiguous attempt, a crash or an expired lease the intent stays `unknown`. What happens next depends on the transport. A transport with `reconcile` asks the provider; it may return `absent` only if no previous call can still perform the effect, and only then is the intent sent again. A transport without `reconcile` cannot prove anything: the worker stops, spends no further attempt and leaves the intent to an operator. The webhook transport has no `reconcile`, and `PROVIDER_RECONCILES` in `packages/core/src/connections/ports.ts` tells the use cases the same.

Every dispatch reloads tenant access, the connection state and pinned versions, the original operator membership or API key capabilities, the erasure register and confirmed list membership. Source preparation is followed by another generic guard and lease check. No provider payload or credential is stored in intents, jobs, attempts or status results. Pause, disconnect, credential rotation, withdrawal or erasure committed before the final guard prevents dispatch; a change after admission cannot recall an admitted call. Every connection state change increments its version, so resuming does not silently repin old intents.

The engine permits at most 60 claim attempts per tenant per minute. Dispatch and reconciliation share a five-attempt automatic budget, with exponential backoff from one minute to at most one hour.

## Operator actions

`connection.intent.list` and `connection.intent.get` expose ids, state, a closed failure class, attempt count, timestamps and `operatorAction`, the one action the admin page, API and MCP may offer next:

- `replay` for a pending intent within its budget, or for an unknown one whose transport can reconcile. `connection.intent.replay` rechecks the generic guards and queues work without clearing uncertainty, leases or backoff. Replay of an unknown intent without reconciliation is refused with `conflict`.
- `resolve` for an unknown intent that cannot be reconciled (today: every unknown webhook). `connection.intent.resolve` marks it `resolved` after the operator has checked the receiver by hand. It is refused while an attempt holds the lease, it is never sent again, and the command's audit row records who closed it.

Both require `connections:replay`. Completed, blocked, failed and resolved intents offer no action.

## Storage

Migration 0025 adds `connection_intents` and append-only `connection_attempts`, both under forced tenant RLS; 0028 narrows their value sets. Both are operational and excluded from portable tenant exports: importing unfinished work into another installation could duplicate effects. Installation backups retain them for recovery. Erasure detaches the supporter id, invalidates the worker lease and preserves anonymous success, uncertainty or manual resolution; pending work becomes blocked. The remaining business id is an opaque UUID, not an address or a submitted payload. This does not assert that an external copy was erased. The form-feed source is installed; Mailchimp observations propagate suppression; external deletion remains an explicit manual action for the named external owner.

## Mailchimp

The account setup reads account identity, audiences and merge-field schemas through `connection.mailchimp.test`, requiring `connections:credentials`. The key is never returned; saving requires entering it again. Connection metadata uses the account id and the closed destination `https://usN.api.mailchimp.com/3.0/lists/<audience>`. Delivery requires a matching key server prefix. Credential replacement rechecks that the key serves the saved account, server and audience; changing accounts requires a new connection. The adapter never follows redirects or accepts a tenant-supplied API origin. Requests have a five-second total deadline and a 1 MiB response limit. Account discovery is bounded and fails rather than silently truncating audiences or mapping fields.

On the connection select allowed forms and the confirmation owner. In the existing form feed, select the same connection version and owner, map the e-mail field to `email` and other fields to exact merge tags such as `FNAME`. Mycel-owned feeds wait for the local confirmation; Mailchimp-owned feeds send pending enrollment and suppress the local confirmation mail and token. A scope and a form each have one confirmation owner, including conditional feeds; at most one enabled external confirmation feed can send its confirmation. An unavailable external owner rejects that marketing submission rather than silently sending a local replacement confirmation.

The feed operation is explicit: `subscribe` creates new members and updates existing profiles without a status change; `profile` updates existing members only; `resubscribe` may change an unsubscribed member when the new submission and confirmation evidence postdate the provider withdrawal. Cleaned, archived and pending members are never silently resubscribed. A new submission is separate evidence; replay of an old intent cannot manufacture it.

Before a provider write, migration 0045 stores an insert-only baseline in `mailchimp_receipts`: tenant, intent, supporter, member hash, prior status and dates. No submitted field values or credential are copied there. The adapter refreshes authorization, erasure, consent and the pinned source after the provider preflight. Lost responses reconcile through a targeted member read. A matching current result can finish the intent; absence never proves a prior call cannot still finish, so an unknown intent never resends blindly. Explicit no-effect 400/401/403/429 responses allow a bounded retry while preserving the original baseline.

Provider-owned consent requires a fresh provider opt-in timestamp after the persisted request baseline, an absent or unsubscribed baseline, current source authorization and the original submission. An already subscribed or pending member is not evidence of this submission's confirmation. Observed suppression removes the local list through the append-only supporter event log. Local or external address changes do not silently transfer another address's consent: old mappings stop or suppress the old address, and a new evidenced signup is needed.

Each copied member has one hourly tenant comparison job, limited to 60 reads per tenant per minute. `connection.callback.get` returns a connection-version-bound token. When `PUBLIC_API_URL` is configured, the admin shows the API URL `/hooks/mailchimp/<token>` to register with the audience. Incoming bodies only trigger an authenticated provider read; their address, status and timestamps are never trusted as consent evidence. Tokens bind tenant and connection version, callback reads are rate limited, and callbacks do not create extra recurring pollers. After a connection edit, update the callback URL. Pause, disconnect, changed versions, suspension and erasure are checked before local mutation and provider effects.

`connection.intent.get/list` include redacted provider status. A pending Mailchimp member is shown as waiting for confirmation. Erasure removes the member hash and stops polling; disconnect deletes the credential. Neither action claims deletion of the external copy: status and the admin instructions require manual action by the external owner. Receipts, credentials and unfinished delivery work are operational, excluded from tenant exports; portable connection metadata requires reconnecting after import.

The deterministic browser fixture uses a loopback HTTP server and synthetic account, audience and members. `MAILCHIMP_FIXTURE_ORIGIN` accepts only a loopback origin and is rejected in production. It proves the local contract, not a live account, audience configuration, sender domain or production DNS. Activation still requires the real provider and sender checks in [forms](forms.md).

Provider references checked on 2026-11-10: [member upsert](https://mailchimp.com/developer/marketing/api/lists/members/upsert-member), [member read](https://mailchimp.com/developer/marketing/api/lists/members/get-member), [audience members](https://mailchimp.com/developer/marketing/api/lists/members/list-members) and [webhooks](https://mailchimp.com/developer/marketing/api-concepts/webhooks). Fixtures under `packages/api/fixtures/mailchimp/` use documented response shapes and synthetic data.
