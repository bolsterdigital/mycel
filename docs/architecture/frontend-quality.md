# Frontend quality as a delivery contract

Mycel targets Lighthouse **100/100/100/100** for public, indexable pages: Performance, Accessibility, Best Practices and SEO. This is a product requirement adopted on 2026-10-24, not a claim that the current application scores 100. The same standard covers realistic content, translations and supported theme values, not only an empty demo. An accessible and fast authoring interface matters too; intentional `noindex` on admin and private routes must stay intact.

This document specifies the measurements and the feedback into construction under ADR 009, 013, 018, 020 and 022. Rejected: treating a Lighthouse badge as proof of accessibility or user experience, and fixing each page separately after delivery while leaving its shared cause intact.

**Implementation status:** the existing Playwright, axe, registry conformance, no-JavaScript and action-layout gates remain active. The [direct Lighthouse runner](../reference/frontend-quality-runner.md), repeated evaluator, isolated CI shards and weekly/manual matrix are implemented. The first CI observation was 2026-10-26; calibration ends 2026-11-06; deadline blocking, originally due 2026-11-09, is suspended since 2026-10-27 until the product matrix is fully green once (see the runner reference). The runner reports real failures during calibration. Branch-protection enforcement and a fully green matrix are **not established**. Dynamic preview, demanding-theme, manual and field-data gaps remain explicit in the report. Existing gates are described in [testing.md](testing.md); the project skill is [mycel-frontend-quality](../../.agents/skills/mycel-frontend-quality/SKILL.md).

## Measurable acceptance criteria

Each result identifies a route, state, locale, profile and exact SHA. There is no average across pages, categories, devices or locales that can hide a failing cell.

The Lighthouse and 44 px criteria are Mycel product choices, not claims that WCAG demands a Lighthouse score or 44 px for every target. A tool score of 100 is not WCAG certification. Manual tests are empirical: a named task, reproducible state and observable success/failure, rather than “looks accessible”.

## Representative fixtures, from the first build

Do not wait for customer content. Start from the existing composed campaign and article examples and registry fixtures; publish them through real use cases with synthetic tenant data and local media. Give the quality corpus a version/hash and assert that images load, fonts resolve, expected headings/text/controls exist, and the final URL is the intended page before measuring. An empty shell, redirect, login or error page invalidates the sample.

The initial public corpus contains a campaign page with hero, form, CTA and image; and a long article with at least 2,000 words, headings, numbered/bullet lists, links, quotation, floated image and at least four locally generated media assets. These are additional composed fixtures, not a replacement for every block's examples. Include default and a valid demanding theme, nl/en, and empty/error/success interaction states in the existing browser flows. Keep a short/empty document as an edge case, never as the performance benchmark.

Add actual features as they ship: collection/search results with a declared populated size; restricted teaser and authenticated read; media-heavy article; conditional form; managed style; and scripts/embeds before and after consent. A feature PR adds its fixture and applicable states in the same PR. Nested blocks, long translations and editor conflicts belong in the corpus. Do not fake not-yet-built functionality merely to make the matrix complete: show it as planned with its implementation dependency.

The initial admin corpus is the populated content list and native editor. Add the enhanced writer once merged, with the same long article. Authentication uses the existing mock IdP and synthetic accounts, not production cookies. No account, mail, payment or content mutation is performed against production during a measurement.

Third-party integrations have two kinds of evidence: deterministic local contract fixtures in CI, and a separately labelled live observation for the enabled configuration. A mocked embed cannot establish the live provider's cost. An enabled integration remains in the measured page; consent behaviour, isolation and kill switches are never bypassed to reach 100.

## Reproducible measurement protocol

1. Build the exact commit in production mode. Pin Node, Lighthouse/LHCI, Chromium and the runner image/profile; store versions with the result. Use a controlled HTTPS origin/proxy and the production headers, compression and cache configuration. Keep the existing application/authentication database roles; never give the web process owner credentials for measurement convenience.
2. Seed the versioned synthetic corpus. Check status, final URL, content identity, fonts and media. Wait for server readiness. One unmeasured server warm-up per route is allowed and declared; measured browser navigations each start with fresh cache/storage. Also exercise cold server/startup and warm-cache behaviour in the scheduled matrix, with their cache state labelled separately.
3. Run five samples sequentially per URL/state/profile, without competing builds or browser workers on that runner. Use the pinned simulated mobile throttling profile and a separately pinned desktop profile, never compare a laptop's raw timing with CI. Different matrix shards may run on separate isolated runners. Record viewport, device scale, CPU/network throttling, runner class and cache state.
4. Evaluate every sample structurally before scores. Missing categories, Lighthouse runtime errors, absent resources, an unexpected final URL, wrong authentication state, fewer than five samples or changed tool versions produce `inconclusive`, not `pass`. Report all raw scores, metric values, spread and audit IDs. Performance uses the median explicitly; LHCI's optimistic aggregation is not the contract. If any Performance sample is below .98 while the median reaches .995, classify the set as unstable/inconclusive and diagnose the spread.
5. Keep original JSON/HTML, manifest, network summary and traces required for diagnosis as artifacts. A deterministic accessibility or functional failure is a failure immediately. For inconclusive or performance-only failures, allow one diagnostic batch of five with the same SHA/config; preserve both batches. A rerun does not erase the first failed batch or turn a flaky gate green. The cause must be attributed and corrected before enforcement passes.
6. Compare with the latest successful baseline for the same corpus/tool/runner profile, but evaluate absolute targets independently. First runs report “no baseline”; a baseline below 100 does not redefine the target. Tool upgrades run old/new versions against the same SHA and fixtures in their own PR, with changed audit meanings reviewed. Store history instead of silently rebasing away regressions.

A compact result contains `schemaVersion`, `commit`, `fixtureHash`, `environment`, `route`, `locale`, `state`, `profile`, `sampleIds`, raw category scores and metrics, aggregate result, failed audit IDs, artifact links and any repair address. State is one of `pass`, `fail`, `inconclusive`, `not-measured`; the last three cannot satisfy an enforced check. A scheduled run additionally records the deployed SHA or release. Raw reports may contain page content: use synthetic data, restrict authenticated artifacts, and never upload private reports to LHCI temporary public storage. Retain detailed artifacts for 30 days and small sanitized summaries for 90 days in the project's controlled storage.

## When the checks run

| ------------------------------------------------------------ | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| During construction                                          | Affected fixtures, axe, keyboard and layout assertions in the existing suites; local Lighthouse on the affected route when available.                                                   | Fast feedback before a PR; no need to wait for a rich customer site.                                                                                                   |
| Frontend PR, including assets/dependencies/rendering headers | Default Lighthouse set: both public reference pages on mobile, five samples each; add affected routes/states and desktop for layout/asset changes. Existing `verify` remains mandatory. | Required `frontend-quality` status after rollout; policy/config changes also run it. An unmapped executable change runs the default set rather than silently skipping. |
| Main push and release candidate                              | The same reference set and affected route coverage against the new exact SHA; full matrix before a release.                                                                             | Catches integration differences; release requires all applicable evidence, including manual accessibility.                                                             |
| Weekly and manual dispatch                                   | Full available corpus, nl/en, mobile/desktop, supported demanding theme, cache and consent states; deployed public smoke when a deployment exists.                                      | Drift report with named owners. Disabled schedules or missing artifacts are visible as missing measurement, not healthy status.                                        |
| New block/theme/widget/integration                           | Register example, task/state and resource expectations before implementation; generic suites then discover the fixture.                                                                 | Prevents a feature from bypassing the contract.                                                                                                                        |

The Lighthouse job runs separately from the ten-minute `verify` budget. Start with a ten-minute limit per isolated shard; build once and reuse the artifact. If the corpus outgrows that limit, partition it by route/profile, not by deleting hard cases. Record total runner minutes so the full weekly matrix remains a deliberate cost. Scheduled workflows do not publish code or autonomously merge fixes.

## Rollout without a permanent warning state

1. **Now: policy and construction rules.** Apply existing gates and the fixture-first rule immediately. Deliver the runner, report evaluator and manifest with a real baseline against already implemented routes. The score target is 100; no present score is asserted here.
2. **Bounded calibration.** The first ten working days after the runner's first CI result are an observation window for the new Lighthouse status only. Each failed applicable cell gets a repair address immediately. Existing security, functional and accessibility checks remain blocking. Missing SEO work belongs to the existing representation work, not to a score exception disguised as “planned”.
3. **Enforcement.** Enable the required status as soon as two independent full batches on the same candidate SHA meet the contract and the evaluator's negative fixtures pass, or at the end of that window, whichever comes first. A still-red cell blocks affected frontend delivery/release at the deadline; it does not prolong calibration automatically. Branch-protection enforcement is verified as a separate delivery criterion, not assumed from a green workflow file.
4. **Real sites and field evidence.** Before the first real tenant launches, replace assumptions with a release run on that tenant's representative, privacy-safe content and active integrations. Maintain synthetic CI coverage. Field observations supplement the lab target when sufficient traffic exists; insufficient field data does not block an otherwise proven prelaunch lab gate.

An exception requires an explicit product decision with the exact cell/criterion, reason, compensating evidence, owner, expiry and follow-up. Record it as `waived`, not `pass`, in the release decision; the raw result stays red. A reporter or repairing agent cannot grant itself an exception. Neither third-party cost nor a score of 99 silently changes 100 into a different target.

## Lower scores create repair work, not an endless agent loop

A measurement failure creates a diagnostic record automatically. A triage session reads it and deduplicates against the existing TODO/briefs before claiming repair work. CI emits sanitized proposals as artifacts; the private planning sibling owns the task ledger. Do not give a public/fork workflow credentials to rewrite that private ledger. Until an authorized consumer exists, the next session of the owner of the affected area explicitly consumes the report. A report without an owner/address is unfinished triage.

| Observed cause                                                         | Repair track                                                            | Typical durable prevention                                                                                                     |
| ---------------------------------------------------------------------- | ----------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------ |
| Slow rendering, large assets or layout shifts                          | Rendering/assets; content owner, platform owner for adapter/proxy work  | Shared image sizing/loading rules, font strategy, bundle boundary and representative asset fixture.                            |
| Names, contrast, focus, keyboard or reflow failure                     | Components/accessibility; owner of the affected public or admin surface | Native/shared component correction, validated theme constraints and stateful fixture in the existing axe/keyboard/layout gate. |
| Indexability, canonical, locale or stale representation                | Publication/SEO; content owner                                          | Fix the common projection/metadata producer and its multi-locale representation conformance tests.                             |
| Consent, unsafe integration, permissions or leakage                    | Security/integration; existing module owner                             | Preserve the privacy boundary; add rejection and accepted-state fixtures. Security changes retain their review tier.           |
| Browser/runner/certificate drift, missing result or noisy measurements | Measurement infrastructure; platform owner                              | Pinned environment, explicit readiness/page identity check and evaluator regression. No score suppression.                     |

Give each distinct root cause one existing task address, or one child of the frontend-quality item if none exists. One CSS defect across twenty routes is one repair, not twenty tickets. Each repair has: user impact, six-field evidence record, exact failing cell and SHA, owner, tier, hypothesis, bounded change, red-before/green-after proof, prevention change and rerun command. At most three independent tracks are active; the rest remain ordered. Shared files are sequenced. No new auth/security/data-loss work is relabelled workhorse merely because Lighthouse found it.

The owning build session may implement a claimed repair within that scope. Review sessions only record findings and hand them off, following [review.md](review.md). Two unsuccessful repair/measurement iterations trigger a fresh diagnosis and a documented choice of next experiment; do not keep rerunning, spawning agents or expanding scope indefinitely. Escalate an actual product trade-off to the owner; routine implementation does not need a new product decision.

Closure requires the failing fixture to pass on the repaired SHA in the same environment, the other affected criteria to remain green, and the prevention to be in the closest reusable gate. Preserve normal independent review and merge rules. For an issue that cannot be automated, improve the named manual task and release checklist, and retain observed evidence instead of pretending it is covered.

## Improve the factory, retain the safety net

For every confirmed defect, ask why the existing fixture, validator or component allowed it. Prefer moving correctness earlier: schema validation for impossible theme choices; image processing that emits dimensions and variants; components with intrinsic labels and keyboard semantics; registry fixtures that generate coverage for all block types; one publication projection for every representation. The fix belongs there, with a representative failing example. Do not accumulate agent instructions as a substitute for executable constraints.

Use a weekly summary from the first runner result:

- **First-pass rate:** frontend PR heads whose first valid batch passes / all frontend PR heads with a valid first batch. Count inconclusive/missing batches separately; reruns never replace first results.
- **Escapes and recurrence:** confirmed defects found after merge, grouped by root-cause class; whether the same class recurs after its prevention merged. Target zero recurrence of a class claimed to be prevented.
- **Prevention completion:** every closed defect has red-before/green-after evidence in a reusable gate, or explicit manual coverage and its limitation. Target 100% of closed defects; no “fixed locally” closure.
- **Repair effort and feedback cost:** time from first failing report to confirmed fix, active repair minutes, CI minutes, rerun rate and false alarms. Diagnose the environment if false alarms grow; do not relax the product target.
- **Coverage debt:** implemented routes/variants/states without required evidence, and expired calibration/exception records. Target zero unowned gaps and zero overdue exceptions.

The first ten frontend PRs establish the process baseline; report numerator/denominator, not an invented improvement percentage. Compare the next ten with it and choose one demonstrated bottleneck to improve. Keep the score gate after the factory improves: its success is that it usually finds nothing and costs little, not that empirical checks disappear. Existing review budgets remain in force; a scheduled diagnostic run is not permission for an unbounded review audit.

## Tests for the measurement system itself

The implementation must demonstrate these cases before its status becomes required:

1. A representative good fixture produces five valid reports and passes the declared contract; Performance 99, any deterministic category below 1, and a missing/null category fail their applicable criteria.
2. A best-of-five score of 100 with a median below .995 fails; one very slow sample with an otherwise passing median is inconclusive. A second batch retains the first result and cannot silently overwrite its state.
3. A login redirect, 404, missing image, wrong locale, empty shell, wrong SHA/tool profile or missing sample cannot pass. Scheduled/live and CI evidence cannot be mixed.
4. Admin SEO is not applicable while `noindex` remains required; public SEO stays applicable. A consent fixture that gains performance by hiding the enabled integration fails fixture/network expectations.
5. The same root cause on several routes maps to one repair proposal; a later run updates that record. A closed class that reappears is a recurrence, and expired exceptions remain visible.

Grow the existing browser/conformance suites for product defects. A small evaluator unit suite is justified for the new aggregation and classification logic; do not build a parallel application test framework.

## Sources and interpretation

Google documents [performance score variability](https://developer.chrome.com/docs/lighthouse/performance/performance-scoring) and [LHCI repetition and aggregation](https://googlechrome.github.io/lighthouse-ci/docs/configuration.html). These justify fixing the environment and retaining repeated samples; the thresholds, cadence and rollout above are Mycel choices.

[Lighthouse accessibility scoring](https://developer.chrome.com/docs/lighthouse/accessibility/scoring) excludes manual checks from the score. [W3C's evaluation guidance](https://www.w3.org/WAI/test-evaluate/tools/selecting/) explains why automated tools need human judgement. The contract therefore keeps manual tasks alongside automation. [W3C reflow guidance](https://www.w3.org/WAI/WCAG22/Understanding/reflow.html) distinguishes a 320 CSS px viewport from text enlargement; the combined stress test is an additional Mycel requirement. [Web Vitals](https://web.dev/articles/vitals) supplies the real-user metric definitions and good thresholds, not a guarantee derived from a lab score.
