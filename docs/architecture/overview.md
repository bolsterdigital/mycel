# Architecture overview

Short map; the reasoning is in [`../adr/`](../adr/).

```
                 ┌──────────────┐  ┌──────────────┐  ┌──────────────┐  ┌──────────┐
   fronts        │ apps/web     │  │ packages/api │  │ packages/mcp │  │  CLI     │
                 │ SvelteKit    │  │ Hono (HTTP)  │  │ MCP server   │  │ (later)  │
                 └──────┬───────┘  └──────┬───────┘  └──────┬───────┘  └────┬─────┘
                        └─────────────────┴────────┬────────┴───────────────┘
                                                   ▼
                 ┌────────────────────────────────────────────────────────────┐
   domain        │ packages/core                                              │
                 │ tenants · content (blocks) · forms · supporters (events)   │
                 │ donations (ledger) · mailing · i18n · use-case registry    │
                 │ ports: Repository, Clock, Ids, PaymentProvider, Mailer,    │
                 │        EventBus, BlobStore, ImageProcessor, MediaDelivery, │
                 │        Logger, ErrorReporter                               │
                 └───────────────┬───────────────────────┬────────────────────┘
                                 ▼                       ▼
   adapters      ┌──────────────────────┐   ┌──────────────────────────────┐
                 │ packages/db          │   │ packages/payments-mollie     │
```

**Rules of the picture** (enforced by `npm run lint:deps`):

- Arrows point down only. `core` imports nothing from the other workspaces and no I/O library.
- Fronts call use cases from `core`'s registry. They do not call adapters directly; they receive adapter instances through composition in `packages/api/src/compose.ts` (and the equivalent in `apps/web`).
- Adapters implement ports from `core`. They do not import each other.
- `packages/observability` (logs, request context, error reporting, metrics) imports only `core`; the fronts import it, `core` never does. Core code logs through `ctx.log` (the `Logger` port) and scrubs error text it stores with `scrubText` (`core/util/scrub.ts`), which the package reuses.

**One registry, many fronts.** Every use case registers with a name, an input schema, an output schema and a required capability. `packages/api` turns the registry into HTTP routes plus an OpenAPI document; `packages/mcp` turns it into MCP tools and resources; `apps/web` calls it in `+page.server.ts` actions. Adding a use case touches `core` once.

**Adding a use case** takes three steps, and the rest follows:

1. Write the function and its Zod `input` and `output` in `packages/core/src/<module>/service.ts` with `defineUseCase`: a dotted name, a one-sentence `description`, the `requires` capability, an `effect` if it publishes, sends, exports or refunds (ADR 018 rule 5), and at least one entry in `examples`.
2. Add it to `useCases` in `packages/core/src/use-cases.ts`.
3. Run `npm run verify`. `POST /v1/<name>` (plus `GET` for a flat query), the OpenAPI operation, the MCP tool (and resource, if it declares one) and the registry conformance suites in core, api and mcp now cover it; `checkRegistry` in `registry-rules.ts` says what is missing.

**Tenant context** is set by the front from authentication and passed into `core` as a `Principal` (tenant, actor, capabilities). `packages/db` turns it into `set_config('app.tenant_id', ...)` per transaction; RLS does the rest (ADR 002). For a public page the tenant is the site being visited: `apps/web/src/hooks.server.ts` resolves the `Host` header through `SiteDirectory` (a core port; `createSiteDirectory` in `packages/db` reads `tenant_hostnames` as `mycel_auth`, cached per hostname for thirty seconds) and puts the site on `locals.site`; a non-primary hostname is a 301 to the primary, an unverified custom hostname a 404, and on a development host the first path segment names the tenant (ADR 014, `docs/reference/hostnames.md`). The universal `reroute` hook puts the slug in front of the path internally so one set of `(public)/[tenant]/...` handlers serves both forms. `mycel_app` reads tenants through the `tenant_directory` view (id, slug, name, locales), never the table. Absolute site URLs come from `siteUrl` in `core/tenants/url.ts` and nowhere else.

**Authentication** happens before a tenant is known, so it reads through its own role. `IdentityStore` (a core port, `createIdentityStore` in `packages/db`) runs each lookup in a transaction that does `set local role mycel_auth`, the one role that may read memberships and API keys across tenants and write logged-in operators (ADR 011 rule 1, migration 0007). The fronts reach it through the `mycel_authenticator` login (`AUTH_DATABASE_URL`), which has no rights except entering that role; web and API never use the schema owner for it. `core/operators/authenticate.ts` turns the answers into principals: an API key (`Authorization: Bearer`, HTTP) or the same key acting as an MCP agent session gets exactly the key's capabilities, looked up on every request so revocation is immediate; an operator in the web admin gets the capabilities of their membership of the tenant in the `/admin/{tenant}` URL, read per request. The operator's browser session is a signed, stateless cookie (`core/operators/session.ts`, 12 hours, `Path=/admin`) that names the operator and nothing else. Login is OIDC (authorization code with PKCE, `openid-client` in `apps/web/src/lib/server/oidc.ts`); development and the e2e gate use `scripts/mock-oidc.mjs`. Managing members and keys is ordinary use cases (`tenant.members.*`, `tenant.keys.*`, all `tenant:admin`) running as `mycel_app` under RLS.

**Entitlements** (ADR 015, TODO #16) are a document per tenant on `tenants.entitlements`, plus `tenants.status`, set only through the platform functions in `packages/db/src/platform.ts` (the `/platform/*` API behind `PLATFORM_API_TOKEN`, and `npm run platform`; `docs/reference/platform-api.md`). They are **loaded** before the tenant context, with whatever establishes it: `IdentityStore.tenantAccess` for an API key, an MCP session or an admin membership, and `SiteDirectory.resolve` (same query, same thirty-second cache) for a public page; `mycel_app` never sees either column. They are **carried** on the `Principal` as the effective document (the stored one merged over `DEFAULT_ENTITLEMENTS`, which grant everything and keep the credit on) and `tenantStatus`; caps are enforced where growth starts, at a person's action, so background work does not fail on one. A tenant job carries the tenant's current access (`tenantJob` loads it with `IdentityStore.tenantAccess` just before it runs), and a handler that publishes calls `requireActive`, the same answer `guardSuspended` gives a command; outbox subscribers keep the defaults of `systemPrincipal`, because ingest is not growth (the seat was reserved at the signup, `ctx.admissions`) and a confirmation mail belongs to a signup accepted before any suspension. They are **enforced** in core only: `guardSuspended` in `Invoker.run` refuses every command but exports for a suspended tenant, and a use case that grows something declares `consumes: '<limit>'` and calls `withinLimit` (or `requireEntitled` for a switch); the registry conformance runs each such use case with that limit at zero, and `checkRegistry` makes a create, invite, add, submit or upload command say `consumes`, even if only `null`. Usage is counted on demand in the tenant's transaction (`ctx.usage`, `tenant.usage`).

**Media** (TODO #10, `docs/reference/media.md`) is a register per tenant (`media`, `media_usages`, migration 0012) with the bytes behind three ports: `BlobStore` (storage: `@mycel/blob`, a directory or a private S3-compatible bucket), `ImageProcessor` (processing: `@mycel/media-sharp`, which probes the header, applies the EXIF orientation and writes no metadata) and `MediaDelivery` (where a variant is served: `appDelivery` in core, `/media/<id>/<file>` on the site itself). Content refers to a media id, never to a URL. `media.upload` renders every variant before it takes the tenant's media lock, then counts `media.storage_max_bytes` and writes files and row under it; `media.delete` refuses while `media_usages` has rows and plans `media.purge` in its own transaction; the daily `media.orphans` platform job sweeps each tenant in its own unit of work as `mycel_app`. The site serves a public variant with `immutable` caching and a restricted one only with a signed path; the original has no public route. The media admin downloads it through a session-authorized route with a ten-minute signed path (`docs/reference/media.md`).

**Events.** Modules communicate through `EventBus` (a port). The first implementation is an in-process bus backed by a Postgres outbox table so that a crash never loses an event; a worker drains it. The supporter module is the main subscriber (ADR 003).

**Supporter identity and fold.** Ingest locks the event's e-mail address (a transaction-scoped advisory lock per tenant and address), resolves it to a stable `supporter_id` (a new UUIDv7 on first sight), appends the event to the monthly partitioned `events` log (dedup on the deterministic id) and folds it into the `supporters` projection. The projection records `appliedThrough`, the fold position (`occurred_at`, then id) of the last event it applied: a newer event is applied on top, a late one triggers a re-fold of that one supporter from its log, so every arrival order ends in the same projection. An address changes only through `supporters.email.change`, which locks both addresses and logs `supporter.email_changed` (ADR 019 rules 1 to 3). Monthly partitions are created by `migrate` up to three months ahead and kept going by the worker's monthly `events.partitions` job; a backfill calls `ensureEventPartitions` for its own range first.

**Background work** runs in one worker process (`Runtime.startWorker`, `packages/api/src/worker.ts`) over two Postgres queues, both claimed across tenants as `mycel_worker` with `FOR UPDATE SKIP LOCKED` so several workers can run (ADR 011). The **outbox** carries committed domain events to subscribers. The **jobs** table (migration 0009, `packages/db/src/jobs.ts`) carries work planned for a time: a use case plans one with `ctx.jobs.enqueue` inside its own transaction (the core's `Scheduler` port; `mycel_app` may insert under its own tenant and nothing more), with a deterministic key (`hostnames.reverify:<tenant>:<hostname>`, `rate_limits.sweep:<hour>`) of which only one can be open. A claim is a five-minute lease: one short transaction stamps `claimed_at` and counts the attempt, the handler runs without a lock on the queue, and a second short transaction marks the job done (and plans its next run when the handler asks) or retries it with the outbox's backoff; a worker that dies leaves the lease to expire, and a job that exhausts its attempts stays in the table with `last_error`. Handlers are registered by type in `packages/api/src/jobs.ts`: a tenant job runs in a unit of work under a `system` principal as `mycel_app` (ADR 011 rule 3), a platform job (`tenant_id` null) on the operator connection under its own role, such as `mycel_janitor` for the hourly rate-limit sweep. Recurring platform jobs (`events.partitions` monthly, `rate_limits.sweep` hourly, `media.orphans` and `jobs.retention` daily) are planned by the worker itself, one row per period. Job types and their payload schemas live in `core/jobs/types.ts`.

**Observability** (TODO #17a, `docs/reference/observability.md`). Every process writes one JSON object per line with `service`, the request or job context (`requestId`, `tenantId`, `job`, `eventId`, from an `AsyncLocalStorage` the front or worker opens) and never an e-mail address: the logger scrubs every string value and drops keys such as `email` and `input`. Unexpected failures (not a `UseCaseError`) go to the `ErrorReporter`: a log line always, and a Sentry envelope to `ERROR_REPORTING_DSN` (GlitchTip) when set. `/healthz` is liveness only; `/readyz` checks the database (api, web) or the loops and queue lag (worker, `queueLag` as `mycel_worker`); `/metrics` is Prometheus text on the api (behind `METRICS_TOKEN`) and on the worker's health port. Finished jobs are deleted after `JOBS_RETENTION_DAYS` by the daily `jobs.retention` job under a restrictive delete policy that cannot reach an open job (migration 0014).

**External effects get an intent row first** (ADR 019 rule 6). A subscriber that calls a provider claims a `mail_sends` row (key `<subscriber>:<event id>`) in one conditional upsert and, in the same committed transaction, plans the job `mail.reconcile` on the jobs table; then it calls the provider outside any transaction and records `sent_at` and the provider id. A provider without idempotency keys can only list what it accepted (`Mailer.lookup`), so reconciliation counts the listed ids against sibling intents with the same correlation hash and resends only when the count proves the attempt never arrived; anything ambiguous stays `unknown` until the job gives it up as `abandoned`. `packages/core/src/mailing/delivery.ts` is the one implementation (`sendOnce`, `settleIntent`, `reconcileMail`); the contract, the states and the residual risk are in `docs/reference/mail.md`.

**Where things live**

| Path                            | Contents                                                                                              |
| ------------------------------- | ----------------------------------------------------------------------------------------------------- |
| `packages/core/src/<module>/`   | `model.ts` (types, schemas), `service.ts` (use cases), `ports.ts`, `events.ts`, tests                 |
| `packages/core/src/registry.ts` | the use-case registry every front reads                                                               |
| `packages/db/migrations/`       | plain SQL, forward-only, one file per change, RLS policy next to the table                            |
| `packages/api/src/`             | Hono app, composition root, API-key authentication, route generation, OpenAPI                         |
| `packages/mcp/src/`             | MCP server over stdio (one API key per process), tool/resource generation                             |
| `packages/observability/src/`   | JSON logger with redaction, request context, error reporters, Prometheus registry                     |
| `apps/web/src/routes/(public)/` | tenant sites, rendered from blocks                                                                    |
| `apps/web/src/routes/(admin)/`  | operator admin behind OIDC, on the platform origin only (ADR 014 rule 4)                              |
| `docs/reference/`               | hostnames and custom domains, the Caddy on-demand TLS example, the platform API, media, observability |
| `docs/adr/`                     | decisions; `docs/plans`                                                                               | private planning sibling (symlink) |
