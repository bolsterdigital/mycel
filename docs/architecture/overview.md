# Architecture overview

Short map; the reasoning is in [`../adr/`](../adr/).

```
                 ┌──────────────┐  ┌──────────────┐  ┌──────────────┐  ┌──────────┐
   fronts        │ apps/web     │  │ packages/api │  │ packages/mcp │  │  CLI     │
                 │ SvelteKit    │  │ Hono (HTTP)  │  │ MCP server   │  │ mycel    │
                 └──────┬───────┘  └──────┬───────┘  └──────┬───────┘  └────┬─────┘
                        └─────────────────┴────────┬────────┴───────────────┘
                                                   ▼
                 ┌────────────────────────────────────────────────────────────┐
   domain        │ packages/core                                              │
                 │ tenants · content (blocks) · forms · supporters (events)   │
                 │ donations (ledger) · mailing · i18n · use-case registry    │
                 │ ports: Repository, Clock, Ids, PaymentProvider, Mailer,    │
                 │        EventBus, BlobStore, ImageProcessor, MediaDelivery, │
                 │        Logger, ErrorReporter                               │
                 └───────────────┬───────────────────────┬────────────────────┘
                                 ▼                       ▼
   adapters      ┌──────────────────────┐   ┌──────────────────────────────┐
```

**Rules of the picture** (enforced by `npm run lint:deps`):

- Arrows point down only. `core` imports nothing from the other workspaces and no I/O library.
- Fronts call use cases from `core`'s registry. They do not call adapters directly; they receive adapter instances through composition in `packages/api/src/compose.ts` (and the equivalent in `apps/web`).
- Adapters implement ports from `core`. They do not import each other.
- `packages/observability` (logs, request context, error reporting, metrics) imports only `core`; the fronts import it, `core` never does. Core code logs through `ctx.log` (the `Logger` port) and scrubs error text it stores with `scrubText` (`core/util/scrub.ts`), which the package reuses.

**Accepted extension direction, not current implementation** ([ADRs 022 to 024](extensibility.md)). A trusted operator-installed extension will declare its core/schema compatibility, owner, capabilities, render and admin contracts, locale, preview, export, fallback and migrations. Activation and browser asset loading can be scoped to a site or page, but do not isolate code executing in the host process. Core remains framework-free and exposes typed ports; untrusted backend execution stays across an authenticated external service boundary. Site-only tenants may keep an external CRM, mail platform or subscription owner through registered connections. The current composition root, block registry, theme and outbox do not yet implement a general extension loader, configurable form action editor or connector inventory.

**Running it** (PR #28). One image, several entrypoints (`Dockerfile`, `docker/entrypoint.sh`); `compose.yml` runs them on one box with Postgres and Caddy, each process with only the database login ADR 011 gives it (`docs/self-hosting.md`). The `mycel` CLI (`packages/api/src/cli.ts`) is the self-hoster's front: platform functions on the owner connection, and `setup`, which creates a tenant there and then invites and adds hostnames through the registry like any front. A tag `vX.Y.Z` publishes that image to GHCR (`.github/workflows/release.yml`, cut with `npm run release`); what an upgrade may rely on is `docs/upgrading.md` (PR #29).

**One registry, many fronts.** Every use case registers with a name, an input schema, an output schema and a required capability. `packages/api` turns the registry into HTTP routes plus an OpenAPI document; `packages/mcp` turns it into MCP tools and resources; `apps/web` calls it in `+page.server.ts` actions. Adding a use case touches `core` once.

**Adding a use case** takes three steps, and the rest follows:

1. Write the function and its Zod `input` and `output` in `packages/core/src/<module>/service.ts` with `defineUseCase`: a dotted name that follows the naming rule below, a one-sentence `description`, the `requires` capability, an `effect` if it publishes, sends, exports or refunds (ADR 018 rule 5), and at least one entry in `examples`.
2. Add it to `useCases` in `packages/core/src/use-cases.ts`.
3. Run `npm run verify`. `POST /v1/<name>` (plus `GET` for a flat query), the OpenAPI operation, the MCP tool (and resource, if it declares one) and the registry conformance suites in core, api and mcp now cover it; `checkRegistry` in `registry-rules.ts` says what is missing.

**Use-case names**. A name is an HTTP path, an MCP tool and an OpenAPI operation at once, and an external agent learns it, so it says what it works on and what it does: `<module>.<entity>.<verb>`, or `<module>.<verb>` when the module is the entity (`media.get`, `connection.pause`). One word per concept, singular: `connection`, `supporter`, `form`, `tenant.member`. `site` is the only prefix for site settings (`site.theme.*`, `site.chrome.*`, `site.brand.*`); `tenant` holds members, keys, hostnames, exports and limits (ADR 017: a tenant is one site, the split is between what a visitor sees and who runs it). An entity that exists once per tenant keeps its own name (`assist.settings`, `tenant.usage`, `tenant.entitlements`, `ops.status`). Verbs are `create`, `get`, `list`, `update` and `delete`, plus domain verbs the plain ones would misname, each listed with its reason in `VERBS`: `remove` undoes `add`, `invite` or `insert` (the thing outlives its place, like an operator or a block in an older revision), `delete` undoes `create` or `upload` (the thing stops existing). Block operations work on `content.block.*` and items on `content.item.*` (ADR 020). `checkRegistry` enforces the module list, the verb list, singular entities and at most three segments; widening a list is a reviewed change to `registry-rules.ts`. Job types, audit operations, event names, error codes and i18n keys share the dotted notation but are not use cases. Accepted ADRs and applied migrations keep the names of their day (`tenant.usage` in ADR 015 is `tenant.usage.get`); the registry is authoritative.

**Tenant context** is set by the front from authentication and passed into `core` as a `Principal` (tenant, actor, capabilities). `packages/db` turns it into `set_config('app.tenant_id', ...)` per transaction, as `mycel_app` (every `tenant_isolation` policy is bound to that role since migration 0018, so even the schema owner does tenant work only by entering it); RLS does the rest (ADR 002). For a public page the tenant is the site being visited: `apps/web/src/hooks.server.ts` resolves the `Host` header through `SiteDirectory` (a core port; `createSiteDirectory` in `packages/db` reads `tenant_hostnames` as `mycel_auth`, cached per hostname for thirty seconds) and puts the site on `locals.site`; a non-primary hostname is a 301 to the primary, an unverified custom hostname a 404, and on a development host the first path segment names the tenant (ADR 014, `docs/reference/hostnames.md`). The universal `reroute` hook puts the slug in front of the path internally so one set of `(public)/[tenant]/...` handlers serves both forms. `mycel_app` reads tenants through the `tenant_directory` view (id, slug, name, locales), never the table. Absolute site URLs come from `siteUrl` in `core/tenants/url.ts` and nowhere else. A public page is rendered by `apps/web/src/lib/blocks/`: one resolver fetches every reference of the published projection (media, forms, linked items) into a plain render model, and the components and the Markdown renderer are pure functions of that model; the theme is a hashed stylesheet route (`docs/reference/theme.md`). Content paths follow one grammar (`/<slug>`, `/articles/<slug>`, a `/<locale>` prefix for every locale but the site's default; `apps/web/src/lib/server/content-route.ts`), carry canonical and `hreflang` links, and are publicly cacheable with a strong ETag that `hooks.server.ts` turns into a 304 (`lib/server/http-cache.ts`).

**Authentication** happens before a tenant is known, so it reads through its own role. `IdentityStore` (a core port, `createIdentityStore` in `packages/db`) runs each lookup in a transaction that does `set local role mycel_auth`, the one role that may read memberships and API keys across tenants and write logged-in operators (ADR 011 rule 1, migration 0007). The fronts reach it through the `mycel_authenticator` login (`AUTH_DATABASE_URL`), which has no rights except entering that role; web and API never use the schema owner for it. `core/operators/authenticate.ts` turns the answers into principals: an API key (`Authorization: Bearer`, HTTP) or the same key acting as an MCP agent session gets exactly the key's capabilities, looked up on every request so revocation is immediate; an operator in the web admin gets the capabilities of their membership of the tenant in the `/admin/{tenant}` URL, read per request. The operator's browser session is a signed, stateless cookie (`core/operators/session.ts`, 12 hours, `Path=/admin`) that names the operator and nothing else. Login starts and callbacks are rate limited per keyed client-address hash, 20 per 10 minutes, counted in `login_attempts` through `IdentityStore.loginAttempt` so every web process shares one window (migration 0018). Login is OIDC (authorization code with PKCE, `openid-client` in `apps/web/src/lib/server/oidc.ts`); development and the e2e gate use `scripts/mock-oidc.mjs`. Managing members and keys is ordinary use cases (`tenant.member.*`, `tenant.key.*`, all `tenant:admin`) running as `mycel_app` under RLS.

**Entitlements** (ADR 015, PR #12) are a document per tenant on `tenants.entitlements`, plus `tenants.status`, set only through the platform functions in `packages/db/src/platform.ts` (the `/platform/*` API behind `PLATFORM_API_TOKEN`, and `npm run platform`; `docs/reference/platform-api.md`). They are **loaded** before the tenant context, with whatever establishes it: `IdentityStore.tenantAccess` for an API key, an MCP session or an admin membership, and `SiteDirectory.resolve` (same query, same thirty-second cache) for a public page; `mycel_app` never sees either column. They are **carried** on the `Principal` as the effective document (the stored one merged over `DEFAULT_ENTITLEMENTS`, which grant everything and keep the credit on) and `tenantStatus`; caps are enforced where growth starts, at a person's action, so background work does not fail on one. A tenant job carries the tenant's current access (`tenantJob` loads it with `IdentityStore.tenantAccess` just before it runs), and a handler that publishes calls `requireActive`, the same answer `guardSuspended` gives a command; outbox subscribers keep the defaults of `systemPrincipal`, because ingest is not growth (the seat was reserved at the signup, `ctx.admissions`) and a confirmation mail belongs to a signup accepted before any suspension. They are **enforced** in core only: `guardSuspended` in `Invoker.run` refuses every command but exports for a suspended tenant, and a use case that grows something declares `consumes: '<limit>'` and calls `withinLimit` (or `requireEntitled` for a switch); the registry conformance runs each such use case with that limit at zero, and `checkRegistry` makes a create, invite, add, submit or upload command say `consumes`, even if only `null`. Usage is counted on demand in the tenant's transaction (`ctx.usage`, `tenant.usage.get`).

**Media** (PRs #15 and #16, `docs/reference/media.md`) is a register per tenant (`media`, `media_usages`, migration 0012) with the bytes behind three ports: `BlobStore` (storage: `@mycel/blob`, a directory or a private S3-compatible bucket), `ImageProcessor` (processing: `@mycel/media-sharp`, which probes the header, applies the EXIF orientation and writes no metadata) and `MediaDelivery` (where a variant is served: `appDelivery` in core, `/media/<id>/<file>` on the site itself). Content refers to a media id, never to a URL. `media.upload` renders every variant before it takes the tenant's media lock, then counts `media.storage_max_bytes` and writes files and row under it; `media.delete` refuses while `media_usages` has rows and plans `media.purge` in its own transaction; the daily `media.orphans` platform job sweeps each tenant in its own unit of work as `mycel_app`. The site serves a public variant with `immutable` caching and a restricted one only with a signed path; the original has no public route. The media admin downloads it through a session-authorized route with a ten-minute signed path (`docs/reference/media.md`).

**Events.** Modules communicate through `EventBus` (a port). The first implementation is an in-process bus backed by a Postgres outbox table so that a crash never loses an event; a worker drains it. The supporter module is the main subscriber (ADR 003).

**Supporter identity and fold.** Ingest locks the event's e-mail address (a transaction-scoped advisory lock per tenant and address), resolves it to a stable `supporter_id` (a new UUIDv7 on first sight), appends the event to the monthly partitioned `events` log (dedup on the deterministic id) and folds it into the `supporters` projection. The projection records `appliedThrough`, the fold position (`occurred_at`, then id) of the last event it applied: a newer event is applied on top, a late one triggers a re-fold of that one supporter from its log, so every arrival order ends in the same projection. An address changes only through `supporter.email.update`, which locks both addresses and logs `supporter.email_changed` (ADR 019 rules 1 to 3). Monthly partitions are created by `migrate` up to three months ahead and kept going by the worker's monthly `events.partitions` job; a backfill calls `ensureEventPartitions` for its own range first.

**Content** (ADR 012, 018, 020, PR #14) is one `content_items` row per page or article, an immutable `content_revisions` row per save holding the whole validated document, and a `content_item_locales` row per locale with the live pointer and the scheduled pin; the status per locale is derived from those pointers. Blocks carry stable ids, rich text is constrained ProseMirror JSON, and every save, publication change and scheduled publish takes the item lock first. Editorial use cases are `authenticatedOnly`, so a public visitor reaches only `content.published.get`, the projection of one published locale of a public page or article, from which the HTML, the JSON read route (`GET /v1/sites/{tenant}/content/{type}/{slug}`, `packages/api/src/content-read.ts`) and MCP all derive. A scheduled publication is a `content.publish` job keyed by item, locale and schedule id. Small edits are block operations by id (insert, move, remove, set_props, split_insert), each one revision on a base; every revision insert also writes its `content_block_refs` rows, which `content.item.find` and live-usage checks read (PR #21). Block types are entries of one registry (`content/block-types.ts`) from which validation, readiness, locale projection and references derive; media references are checked and recorded as usages under the tenant's media lock, which `media.delete` takes too (PR #25). Themes are validated values with one contrast check in `core/theme` (`site.theme.check`; `docs/reference/theme.md`). Details, reserved slugs and the migration of the probe's pages: `docs/reference/content-model.md`.

**Future content extensions** (ADR 022) must preserve those publication, locale and access rules in every representation. A block adds content within `page` or `article`; a type profile adds metadata and presentation over those types; a new domain entity or lifecycle requires another ADR. The effective theme and preview must show the source of each managed override. Current stored blocks and themes remain bounded validated data, with no free CSS field.

**Background work** runs in one worker process (`Runtime.startWorker`, `packages/api/src/worker.ts`) over two Postgres queues, both claimed across tenants as `mycel_worker` with `FOR UPDATE SKIP LOCKED` so several workers can run (ADR 011). The **outbox** carries committed domain events to subscribers. The **jobs** table (migration 0009, `packages/db/src/jobs.ts`) carries work planned for a time: a use case plans one with `ctx.jobs.enqueue` inside its own transaction (the core's `Scheduler` port; `mycel_app` may insert under its own tenant and nothing more), with a deterministic key (`hostnames.reverify:<tenant>:<hostname>`, `content.publish:<item>:<locale>:<schedule>`, `rate_limits.sweep:<hour>`) of which only one can be open. A claim is a five-minute lease: one short transaction stamps `claimed_at` and counts the attempt, the handler runs without a lock on the queue, and a second short transaction marks the job done (and plans its next run when the handler asks) or retries it with the outbox's backoff; a worker that dies leaves the lease to expire, and a job that exhausts its attempts stays in the table with `last_error`. Handlers are registered by type in `packages/api/src/jobs.ts`: a tenant job runs in a unit of work under a `system` principal as `mycel_app` (ADR 011 rule 3), a platform job (`tenant_id` null) on the operator connection under its own role, such as `mycel_janitor` for the hourly rate-limit sweep. Recurring platform jobs (`events.partitions` monthly, `rate_limits.sweep` hourly, `media.orphans` and `jobs.retention` daily) are planned by the worker itself, one row per period. Job types and their payload schemas live in `core/jobs/types.ts`.

**Observability** (PR #18, `docs/reference/observability.md`). Every process writes one JSON object per line with `service`, the request or job context (`requestId`, `tenantId`, `job`, `eventId`, from an `AsyncLocalStorage` the front or worker opens) and never an e-mail address: the logger scrubs every string value and drops keys such as `email` and `input`. Unexpected failures (not a `UseCaseError`) go to the `ErrorReporter`: a log line always, and a Sentry envelope to `ERROR_REPORTING_DSN` (GlitchTip) when set. `/healthz` is liveness only; `/readyz` checks the database (api, web) or the loops and queue lag (worker, `queueLag` as `mycel_worker`); `/metrics` is Prometheus text on the api (behind `METRICS_TOKEN`) and on the worker's health port. Finished jobs are deleted after `JOBS_RETENTION_DAYS` by the daily `jobs.retention` job under a restrictive delete policy that cannot reach an open job (migration 0014).

**Audit log** (PR #19, `docs/reference/audit.md`). `Invoker.run` writes one `audit_log` row per command through `ctx.audit`: in the command's own transaction when it succeeds, in a short transaction of its own after the rollback when it is refused or fails, so HTTP, MCP and web are covered by the one code path. A row holds tenant, actor kind and id (never an address), operation, effect, a keyed hash of the input (`ctx.inputHasher`, HMAC under `AUDIT_HASH_KEY`), result, request id and subject id. The platform functions write their own rows as `mycel_platform`; `audit.retention` prunes as `mycel_audit_janitor` (migration 0015). Tenant administrators read their log with `audit.list`.

**Stuck work** (PR #20, migration 0016). Exhausted jobs, dead outbox events and unknown or abandoned mail intents are visible: a tenant's administrators see their own on `/admin/<slug>/status` through `ops.status.get` and recover a job with `ops.job.retry` or `ops.job.close` (module `packages/core/src/ops/`, as `mycel_app` without the payload), with a redacted diagnosis to copy and nothing sent on their behalf; the hoster lists every tenant's as `mycel_ops` through `/platform/ops/*` and `npm run platform -- ops` (`packages/db/src/recovery.ts`, `docs/reference/platform-api.md`).

**Export and erasure** (PR #32, migration 0019). A tenant leaves an installation as an archive of its rows, read as `mycel_app` in its own context, plus its media files, and arrives in another through one transaction (`packages/db/src/export.ts`, `mycel export|import`, `docs/reference/export.md`); every table of the schema is placed in `TABLES` there, so a new one is in or out of the export by decision, never by accident. Erasure is a permanent register (`ctx.erasures.register`) plus an idempotent apply that only the worker and the CLI can run, as the tenant-bound role `mycel_erasure`, and that a restore runs again. A registration is completed once a backup holds it: the backup login records that in `erasure_backups` (PR #39, migration 0021) and `ctx.erasures.status()` reads it.

**External effects get an intent row first** (ADR 019 rule 6). A subscriber that calls a provider claims a `mail_sends` row (key `<subscriber>:<event id>`) in one conditional upsert and, in the same committed transaction, plans the job `mail.reconcile` on the jobs table; then it calls the provider outside any transaction and records `sent_at` and the provider id. A provider without idempotency keys can only list what it accepted (`Mailer.lookup`), so reconciliation counts the listed ids against sibling intents with the same correlation hash and resends only when the count proves the attempt never arrived; anything ambiguous stays `unknown` until the job gives it up as `abandoned`. `packages/core/src/mailing/send-attempts.ts` is the one implementation (`sendOnce`, `settleIntent`, `reconcileMail`); the contract, the states and the residual risk are in `docs/reference/mail.md`.

**Future form actions and connectors** (ADRs 023 and 024) use this intent and reconciliation principle. Form definitions will pin stable field/action ids and versions, evaluate bounded predicates on the server, and plan transactional notifications separately from confirmed marketing actions. A connection will name its domain and consent owner, tenant-authorized destination, credentials, mapping and maintainer; delivery/replay checks current suppression and erasure state. Mycel's own storage and default processors remain in the EU; a tenant-selected external destination is an explicit export. These are accepted contracts, not claims about current form or provider code.

**Where things live**

| Path                             | Contents                                                                                                                                   |
| -------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------ |
| `packages/core/src/<module>/`    | `model.ts` (types, schemas), `service.ts` (use cases), `ports.ts`, `events.ts`, tests                                                      |
| `packages/core/src/use-cases.ts` | every use case; fronts call `buildRegistry()`, the class is in `registry.ts`                                                               |
| `packages/db/migrations/`        | plain SQL, forward-only, one file per change, RLS policy next to the table                                                                 |
| `packages/api/src/`              | Hono app, composition root, API-key authentication, route generation, OpenAPI                                                              |
| `packages/mcp/src/`              | MCP server over stdio (one API key per process), tool/resource generation                                                                  |
| `packages/observability/src/`    | JSON logger with redaction, request context, error reporters, Prometheus registry                                                          |
| `apps/web/src/routes/(public)/`  | tenant sites, rendered from blocks                                                                                                         |
| `apps/web/src/routes/(admin)/`   | operator admin behind OIDC, on the platform origin only (ADR 014 rule 4)                                                                   |
| `docs/reference/`                | hostnames and custom domains, the Caddy on-demand TLS example, the platform API, media, observability, audit, the content model, the theme |
| `docs/adr/`                      | decisions; `docs/plans`                                                                                                                    | private planning sibling (symlink) |
