# Testing strategy

Tests exist to let agents change this codebase without a human re-reading every line. The strategy is therefore: **a few generic conformance suites that grow by themselves** whenever a registry gains an entry, plus a small number of hand-written tests where the domain has real invariants. Per-feature test files that restate the implementation are discouraged.

A suite is named `*.conformance.test.ts` only when it iterates a catalog or registry (the use cases, the block types, the live schema, `TABLES`), so it grows when the catalog does. An assertion lives in one suite: RLS bypass for every role in `rls.conformance`, one audit row per command in core `registry.conformance` (and on Postgres in `rls.conformance`), the 403 without a capability in the registry suites.

## Rules

Accepted but unimplemented contracts in [ADRs 022 to 024](extensibility.md) grow the existing gates as their implementations arrive. Block and editor conformance must exercise managed package manifest compatibility, locales, layout widths, effective-style provenance, preview, fallback and access in HTML, JSON, MCP, search and export. Form/core/registry conformance must cover stable field and action ids, versioned submissions, server-authoritative predicates, inactive values, distinct author/send/export permissions and no-JavaScript operation. Adapter and database conformance must cover tenant-scoped destination authorization, signed outbound webhooks, SSRF protections, encrypted credential access, retries and ambiguous outcomes, confirmation ownership, suppression, safe replay, external erasure status and single charging authority. Public browser checks include a 320px viewport and the largest text setting at 200% zoom, consent/tag route rules, and per-site performance and accessibility when an external integration is enabled. Add these fixtures with delivery; these statements do not claim the gates already exist.

1. **Fixtures live with the thing they describe.** A block module exports `examples`; a use case module exports `fixtures`; a migration that adds a tenant-owned table needs no test, the conformance suite finds it. A registry entry without a fixture fails `verify`.
2. **One gate, `npm run verify`,** and it must stay under ten minutes on CI. When it does not, split by layer into parallel jobs before trimming tests.
3. **Skip or fail, never silently pass.** Suites that need Postgres or Chromium skip locally when the dependency is absent and fail in CI (`E2E_REQUIRED=1`). A suite asks `requireDatabase` (`@mycel/db/testing`) or `requireServices` and `requireInCi` (`@mycel/core/testing`) instead of comparing `E2E_REQUIRED` itself; `scripts/gates/testing-shape.test.mjs` keeps that comparison in one file. `npm run test:collect` (part of `verify`) collects every suite with an empty environment, so a suite that reads its configuration while collecting fails there instead of on a fresh checkout.
4. **No mocks of our own modules.** Ports have in-memory implementations in `packages/core/src/testing`; use those. Mock only the outside world, from recorded payloads. A rule both adapters enforce lives once in core and both call it; `packages/db/src/adapter-rules.test.ts` runs one scenario over memory and Postgres against one expected record, so a rule one adapter keeps on its own shows up as a difference. A new shared rule adds its case there. Suites build on the shared builders, not local copies: `TENANT`, `adminOf`, `principal({...})` (the administrator with only what a case changes), `runSuffix` and `expectCode` in `packages/core/src/testing/fixtures.ts`; `testTenant` (a tenant created as the platform creates one, audit row included), `migrateSchema` and `closeTenantWork` in `packages/db/src/testing.ts`. A builder a second suite needs moves there.
5. **Snapshots are reviewed, not regenerated.** A PR that updates an HTML snapshot says why in the description.
6. **Flaky tests are fixed or deleted the same day**; a quarantine list longer than zero is a drift signal for `merge-housekeeping`.
7. **No coverage percentage gate and no mutation testing.** Coverage is reported for information; the conformance suites are the guarantee.
8. **Accessibility has a manual layer too**: a screen-reader pass per release on the public flows, recorded in the release notes. Axe is a floor, not a ceiling.
9. **Performance budget** (ADR 009 rule 4) is a Playwright assertion on the public page: no client JavaScript beyond the enhancement bundle, fonts self-hosted, images sized.
10. **Test migrations check schema without resetting role passwords.** `verify` runs after `db:migrate` has provisioned the application and authentication logins. Conformance suites call `migrate` with no passwords, including against scratch databases: role passwords are cluster-wide, while the migration lock is per database. RLS catalog checks keep a short `ACCESS SHARE` lock on a partitioned parent until grant checks finish; do not retain names of partitions another suite may drop for a later catalog lookup.

11. **A test hook never asserts inside code that catches.** A hook that runs inside a job or use case whose errors become a state (`runExportJob` marks the export failed) keeps its own failure and the test throws it after the run; otherwise the report names a later symptom (`expected undefined`) instead of the cause. Wait for a condition with a deadline (`expect.poll`), not for a fixed time beside a timer the code runs.

## Local database

CI starts every run on an empty database; a laptop or the dev server reuses one, and that one is shared by every branch and worktree on the machine. Three guards keep a local run telling the truth about the checkout (PR #34):

- **Schema.** `scripts/test-db-preflight.mjs` (Vitest global setup) and `scripts/e2e/e2e.mjs` stop when the database holds a migration this checkout has no file for: a newer branch migrated it, and its suites would prove another schema. Give such a branch its own database, `createdb mycel_<branch>` as the schema owner with the three URLs in `.env` pointing at it, then `npm run db:migrate` and `npm run db:seed`; switch back by pointing them at the old one.
- **One end-to-end run per database.** `scripts/e2e/e2e.mjs` holds an advisory lock for the run and refuses a second one. It checks its ports first (web 4173, API 8797, mock IdP 8798, worker 8796; `E2E_*_PORT` to move them) and names a port that is still taken, usually by an interrupted run.
- **Other sessions.** Both also name every other client session on that database and go on: a running `npm run dev` or an orphaned API keeps its worker draining every tenant's outbox, so a red test that waits for an outbox row or a mail may be theirs (PR #167). The warning is not a refusal, so a dev server may run next to the tests; each pool from `createDb` names its process (`PGAPPNAME`, or entry script and pid; `npm run dev` names its own pid), and an unnamed session is an older checkout or another client.
- **One blob store per database.** Media rows live in the database, their files in `BLOB_DIR`. A relative `BLOB_DIR` (the default `.scratch/blob`) resolves against the main checkout's root, also from a linked git worktree, so every worktree of a clone shares the store as it shares the database. A separate clone on the same database needs an absolute `BLOB_DIR` pointing at the first clone's store. `scripts/e2e/e2e.mjs` stops after its seed when a live medium of tenant probe has no file in the store it serves; the remedy is copying the files from the store that has them (`rsync -a --ignore-existing <other>/tenants/<probe id>/ .scratch/blob/tenants/<probe id>/`), never deleting the rows. Worktrees made before this rule wrote into their own `.scratch/blob`.
- **Hand-delivered outbox work.** A suite that feeds subscribers itself and compares rows over time closes its tenants' work (`closeTenantWork`) right after the fixture, not only in `afterAll`: another checkout's worker on the same database would deliver the events a second time in between (export and erasure conformance, 2026-10-31).
- **Fixture operators.** The mock IdP's issuer includes its port, so a run on another port would log in as new operators without memberships. Before the seed, `scripts/e2e/e2e.mjs` moves the synthetic `@probe.test` operators onto the current mock issuer; the dev operator (`npm run dev`) is left alone. Production keeps issuer plus subject as the identity.

On Linux a local run measures text as CI does. Text measurement depends on the installed fonts: the admin sets `system-ui`, which the CI runner resolves to DejaVu Sans and a dev machine to its own, narrower font, so a button or an ⓘ that fit locally was clipped in CI (PRs #175, #207, #210, #212). `apps/web/playwright.config.ts` therefore points Chromium's fontconfig at `apps/web/e2e/fonts/` (Latin subsets of DejaVu Sans and Sans Mono with Ubuntu's rendering settings), and a heading measures in a local run to the fraction of a pixel what it measures in CI. Chromium on macOS ignores fontconfig: there a local run is no proof for the layout gate, and the CI run on the PR's head is the evidence for a UI change. When the runner image changes its fonts, compare `fc-match system-ui` on the runner with these files.

Run the local `verify` after committing, not before. Gates that read `git ls-files` (the `TODO #` baseline among them) see only committed files, so a green run over an uncommitted change can still turn red in CI (PR #179).

## What a PR needs

The PR description names the conformance suite that grew (or says why none did), the hand-written invariants added, and what could not be run locally. Review reads the fixtures first: if the examples are right, the generic suites have already read the rest. The pull request template asks for exactly that, plus the block `scripts/review-signals.mjs` prints; how a reviewer uses it to pick at most one extra counterproof is [review.md](review.md).

## Frontend quality contract

The [frontend quality contract](frontend-quality.md) defines measurable Lighthouse, accessibility, task, resource and field-performance criteria, repeated measurement, adoption and repair routing. Its status section distinguishes existing gates from planned automation. Add frontend defect fixtures to the existing suites; every repair must also address why construction allowed that defect. Lighthouse is a separate measured job, not a replacement for `verify`, manual accessibility or the security boundaries.
