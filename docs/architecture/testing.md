# Testing strategy

Tests exist to let agents change this codebase without a human re-reading every line. The strategy is therefore: **a few generic conformance suites that grow by themselves** whenever a registry gains an entry, plus a small number of hand-written tests where the domain has real invariants. Per-feature test files that restate the implementation are discouraged.

A suite is named `*.conformance.test.ts` only when it iterates a catalog or registry (the use cases, the block types, the live schema, `TABLES`), so it grows when the catalog does. A hand-written suite against Postgres or HTTP is `*.test.ts`, whatever boundary it guards; reviewers read it as a feature test. An assertion lives in one suite: RLS bypass for every role in `rls.conformance`, one audit row per command in core `registry.conformance` (and on Postgres in `rls.conformance`), the 403 without a capability in the registry suites.

## Rules

Accepted but unimplemented contracts in [ADRs 022 to 024](extensibility.md) grow the existing gates as their implementations arrive. Block and editor conformance must exercise managed package manifest compatibility, locales, layout widths, effective-style provenance, preview, fallback and access in HTML, JSON, MCP, search and export. Form/core/registry conformance must cover stable field and action ids, versioned submissions, server-authoritative predicates, inactive values, distinct author/send/export permissions and no-JavaScript operation. Adapter and database conformance must cover tenant-scoped destination authorization, signed outbound webhooks, SSRF protections, encrypted credential access, retries and ambiguous outcomes, confirmation ownership, suppression, safe replay, external erasure status and single charging authority. Public browser checks include a 320px viewport and the largest text setting at 200% zoom, consent/tag route rules, and per-site performance and accessibility when an external integration is enabled. Add these fixtures with delivery; these statements do not claim the gates already exist.

1. **Fixtures live with the thing they describe.** A block module exports `examples`; a use case module exports `fixtures`; a migration that adds a tenant-owned table needs no test, the conformance suite finds it. A registry entry without a fixture fails `verify`.
2. **One gate, `npm run verify`,** and it must stay under ten minutes on CI. When it does not, split by layer into parallel jobs before trimming tests.
3. **Skip or fail, never silently pass.** Suites that need Postgres or Chromium skip locally when the dependency is absent and fail in CI (`E2E_REQUIRED=1`). `npm run test:collect` (part of `verify`) collects every suite with an empty environment, so a suite that reads its configuration while collecting fails there instead of on a fresh checkout.
4. **No mocks of our own modules.** Ports have in-memory implementations in `packages/core/src/testing`; use those. Mock only the outside world, from recorded payloads.
5. **Snapshots are reviewed, not regenerated.** A PR that updates an HTML snapshot says why in the description.
6. **Flaky tests are fixed or deleted the same day**; a quarantine list longer than zero is a drift signal for `merge-housekeeping`.
7. **No coverage percentage gate and no mutation testing.** Coverage is reported for information; the conformance suites are the guarantee.
8. **Accessibility has a manual layer too**: a screen-reader pass per release on the public flows, recorded in the release notes. Axe is a floor, not a ceiling.
9. **Performance budget** (ADR 009 rule 4) is a Playwright assertion on the public page: no client JavaScript beyond the enhancement bundle, fonts self-hosted, images sized.
10. **Test migrations check schema without resetting role passwords.** `verify` runs after `db:migrate` has provisioned the application and authentication logins. Conformance suites call `migrate` with no passwords, including against scratch databases: role passwords are cluster-wide, while the migration lock is per database. RLS catalog checks keep a short `ACCESS SHARE` lock on a partitioned parent until grant checks finish; do not retain names of partitions another suite may drop for a later catalog lookup.

11. **A test hook never asserts inside code that catches.** A hook that runs inside a job or use case whose errors become a state (`runExportJob` marks the export failed) keeps its own failure and the test throws it after the run; otherwise the report names a later symptom (`expected undefined`) instead of the cause. Wait for a condition with a deadline (`expect.poll`), not for a fixed time beside a timer the code runs.

## Local database

CI starts every run on an empty database; a laptop or the dev server reuses one, and that one is shared by every branch and worktree on the machine. Three guards keep a local run telling the truth about the checkout (PR #34):

- **Schema.** `scripts/test-db-preflight.mjs` (Vitest global setup) and `scripts/e2e.mjs` stop when the database holds a migration this checkout has no file for: a newer branch migrated it, and its suites would prove another schema. Give such a branch its own database, `createdb mycel_<branch>` as the schema owner with the three URLs in `.env` pointing at it, then `npm run db:migrate` and `npm run db:seed`; switch back by pointing them at the old one.
- **One end-to-end run per database.** `scripts/e2e.mjs` holds an advisory lock for the run and refuses a second one. It checks its ports first (web 4173, API 8797, mock IdP 8798, worker 8796; `E2E_*_PORT` to move them) and names a port that is still taken, usually by an interrupted run.
- **Fixture operators.** The mock IdP's issuer includes its port, so a run on another port would log in as new operators without memberships. Before the seed, `scripts/e2e.mjs` moves the synthetic `@probe.test` operators onto the current mock issuer; the dev operator (`npm run dev`) is left alone. Production keeps issuer plus subject as the identity.

## What a PR needs

The PR description names the conformance suite that grew (or says why none did), the hand-written invariants added, and what could not be run locally. Review reads the fixtures first: if the examples are right, the generic suites have already read the rest. The pull request template asks for exactly that, plus the block `scripts/review-signals.mjs` prints; how a reviewer uses it to pick at most one extra counterproof is [review.md](review.md).

## Frontend quality contract

The [frontend quality contract](frontend-quality.md) defines measurable Lighthouse, accessibility, task, resource and field-performance criteria, repeated measurement, adoption and repair routing. Its status section distinguishes existing gates from planned automation. Add frontend defect fixtures to the existing suites; every repair must also address why construction allowed that defect. Lighthouse is a separate measured job, not a replacement for `verify`, manual accessibility or the security boundaries.
