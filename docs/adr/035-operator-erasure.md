# ADR 035 - An operator account is erased by the installation; a stored actor carries an id, never an address

- **Status**: accepted
- **Date**: 2026-11-12
- **Refines**: ADR 009 rule 9 (attribution of every action) and ADR 018 (immutable revisions) for the operator address in a stored actor; ADR 019 rule 8 (every copy, backups) for operator accounts
- **Supersedes**: nothing; ADR 012 rule 4 and ADR 028 keep revisions and plans immutable, except for the one-time migration in rule 4 below
- **Preserves**: ADR 002 tenant isolation, ADR 017 (a tenant is one site), ADR 032 and ADR 034 for supporters and people

## Context

An operator is a human who works in the admin. The `operators` row (address, name, identity-provider issuer and subject, preferences) belongs to the installation, not to a tenant: one account can hold memberships on several sites, and a pending invitation is an `operators` row without a subject. `tenant.member.remove` removes one membership and keeps the account. No route removes the account itself, so the inventory of #169 D lists every operator copy as `planned: operators`.

Every write that records who acted stores the whole `Actor`, and the operator variant holds `operatorId` and `email`. That address therefore sits in current and historical revisions, bulk plans and their effects, form feed settings, connection intents, the outbox, `media.created_by` and `api_keys.created_by`. Revisions and plans are immutable (ADR 012 rule 4, ADR 028). It also sits in `erasures.actor` and `person_erasures.actor`, although migrations 0019 and 0050 and ADR 034 rule 2 say that column holds kind and id, never an address: the code stores `principal.actor` as it is. The admin shows a revision's author as that stored address; the audit view already resolves an id to a name and shows "a team member" for an unknown one.

Three more facts shape the decision. The session cookie is stateless and signed: it carries the operator id, address and name, and an admin request reads only the memberships of that id (and preferences, which default when the row is missing), never the account itself. `tenant.member.remove` revokes the API keys the member created. An export archive names a member by address only, without the operator id, and import writes revisions and plans `as-exported`, so today the address in a stored actor is the only link between imported history and a person; and no platform operation adds a member to an existing tenant.

The address in a stored actor is a copy, not the source: the id identifies the operator, and the account row holds the current address and name.

## Decision

1. **The installation erases an operator account, by explicit operator id.** Operator erasure is a platform operation (`platformOperations`, platform API and the `mycel` command line), not a tenant use case: the account is installation data, may serve several tenants, and no tenant may remove another tenant's member. A tenant's remedy stays `tenant.member.remove`. A request from the human goes to the installation maintainer, who runs the operation with the operator id; the system never derives an operator from an address, a name or an identity-provider subject. An id found neither in `operators` nor in the register of rule 2 is refused as a whole.
2. **An installation register makes the erasure durable.** Each request appends `(operator_id, erased_at)` to an append-only, installation-level register; a second request for a registered id is a no-op. The register holds no address and no name. It outlives every backup (ADR 019 rule 8): after a restore, the erasure step removes every registered operator again before the installation serves requests.
3. **Erasure removes the account, its access and its keys, and keeps the id as an inert reference.** In one transaction it deletes the `operators` row (address, name, issuer and subject, a pending invitation included), every `tenant_memberships` row of that id and the operator's preferences, and revokes on every tenant each API key the operator created, as `tenant.member.remove` does; the result reports the revoked keys per tenant. Ids in revisions, plans, audit rows, API keys, media and registers remain: without the account they identify nobody. Every place that shows an actor resolves the id at read time; an absent or registered id shows as a former team member, localised, never as an address.
   - _Session._ The cookie is not revoked and needs no revocation for tenant access: every admin request reads the memberships of the id, and there are none, so a live session reaches no tenant at once. The cookie still carries the address and name until it expires (at most twelve hours); therefore the admin hook reads the account by id on each request, as it reads preferences now, and treats a missing account as no session: the cookie is cleared and the address is never shown again.
   - _Later login._ The identity-provider account is outside Mycel and stays. A later login with the same subject creates a new account with a new id and no memberships, by the person's own act; it reaches no tenant until a tenant invites it, and nothing links it to the erased id.
   - _Last admin._ Erasure is not refused when it leaves a tenant without a `tenant:admin` member; the result lists those tenants. The repair is part of this decision: a platform operation (`platformOperations`, platform API and command line) that grants `tenant:admin` on an existing tenant to an address, through the same invitation path as `tenant.member.invite` (an existing member gets the capability added, otherwise a pending operator is created), within `operators.max`, audited in that tenant. It applies only while no member of that tenant holds `tenant:admin`, checked under the tenant's membership lock, and is refused otherwise: it repairs a tenant without an admin (after an erasure, or one just created) and is no way for the platform to add an admin beside existing ones (ADR 002).
   - _Tenant trace._ Each affected tenant gets one audit row (`platform.operator.erase`, platform actor, the erased operator only as an id, the number of revoked keys), so a tenant sees that a member left by an installation decision (ADR 009 rule 9). The installation register of rule 2 is the installation's own trace.
4. **A stored actor carries kind and id, never an address.** Every write that persists an actor stores the operator variant as `{ kind: 'operator', operatorId }`; the address stays in the in-memory principal only, for the session. One migration removes `email` from every stored operator actor in long-lived copies (revisions, bulk plans and effects, form feed settings, connection intents, media, API keys, both erasure registers); this is the only in-place change to revisions and plans this ADR allows, it touches no other key, and it is a schema step that runs as the migration owner, not a grant to any role. Short-lived copies (outbox, presence) stop receiving the address and expire on their own term. Because no address is at rest, erasure has nothing to scrub in history; this also makes `erasures.actor` and `person_erasures.actor` what migrations 0019, 0050 and ADR 034 rule 2 already say they are. The migration has a second irreversible effect beside removing the copies: a tenant reads names only of its current members (`member_read`), so history by a member who was removed earlier, but whose account still exists, now also shows as a former team member, for good. The tenant loses the only copy of that address it could read; this is accepted because the tenant removed the member itself, the audit view already shows such a member this way, and the id stays for the audit trail.
5. **Exports, imports and backups follow.** Erasure expires every archive of a tenant where the operator held a membership, as supporter erasures do (ADR 032). A restore of a backup taken before the migration of rule 4 runs that migration before rule 2 re-applies the register.
   - _Import normalises every stored actor._ Whatever an archive holds, import writes each operator actor in the copies of rule 4 as `{ kind: 'operator', operatorId }` and drops every other key, so an archive written before the migration, already downloaded by a tenant, cannot put an address back at rest.
   - _Attribution travels as a mapping._ An archive names each member by address and by its operator id in the source installation (a new archive format version). Import invites each address as `as-invitation` does now and rewrites every operator id in the imported actors and audit rows from the source id to the id the invitation resolved to, so current members keep their history. An actor id without a membership line in the archive (a former member, an erased operator, an archive of the older format) is kept as it is and shows as a former team member.
   - _Registered ids stay erased._ On the installation that erased an operator, an archive membership line whose source id is in the register is skipped and reported, and its history stays anonymous: an archive that carries source ids does not bring an erased operator back. An archive of the older format names a member by address only and the register holds no address, so its membership line becomes an invitation, as when the tenant invites that address by hand; its history stays anonymous. Another installation does not know the register; there the address in an archive the tenant downloaded is the tenant's own copy, outside what the installation can erase, as for every other copy in a download.
6. **Names in free text are not erased.** An operator named in prose, an API-key label, a connection purpose or a pattern name is not found from an operator id; the tenant edits current text through ordinary use cases, and the result of the operation says so rather than reporting "all erased" (as ADR 034 rule 6).

## Rejected alternatives

- A tenant use case `tenant.operator.erase`: one tenant would delete an account that other tenants rely on, or each tenant would erase only its own copy and the account would never go.
- Keeping the address in stored actors and scrubbing it on erasure only: needs an in-place update path on every immutable table for ever, and keeps addresses of living operators in history, exports and backups where the id already suffices.
- A tombstone row in `operators`: keeps a record that only says someone was there; an absent row with an inert id renders the same and holds nothing.
- Removing operator ids from revisions and plans: rewrites attribution structure for no privacy gain once the account is gone, and breaks the audit trail of ADR 009 rule 9.
- Refusing erasure of the last admin of a tenant: a legal erasure cannot wait for a tenant to appoint a successor; the maintainer restores an admin through the platform operation of rule 3.
- Restoring an admin through the tenant use case with a constructed admin principal, as the seed does: a forged principal outside the platform boundary, without the platform audit.
- A restore that works on any tenant: the platform token would become a key to every tenant's data; a sole admin who is unreachable but not erased is a separate decision.
- Leaving an erased operator's API keys active: an erased person would keep working credentials on every tenant they served, weaker than removing one membership.
- Accepting imported history as anonymous for everyone: moving a site between installations would lose the author of every revision, also for people still on the team.
- Keeping the address in the archive actor as the import mapping: it puts addresses back at rest, which rule 4 removes; the membership line already carries the address once.
- Deleting the identity-provider account from Mycel: the IdP is a separate system with its own owner (ADR 008); Mycel only stops recognising the subject.

## Consequences

A migration (number claimed at build) adds the operator register, removes `email` from stored operator actors in the long-lived copies named in rule 4 (in batches; it rewrites every `content_revisions` row, so the lock time is measured), and gives the platform role what erasure and the admin restore need on `operators`, `tenant_memberships`, `api_keys`, `audit_log` and preferences. The actor serialisation becomes one function in core that every persisting adapter uses, with a conformance test that no stored actor carries an address. `actorLabel` and the revision, presence and conflict views resolve an operator id to a name through the members list; an absent id gets the existing "a team member" wording. Both operations (erase, restore an admin) join `platformOperations`, the platform API and the command line; the restore drill re-applies the register. The admin hook reads the account per request instead of only its preferences. The export format gains the source operator id per membership line and import gains the actor normalisation and id mapping; an archive of the older format still imports. `STORAGE` replaces every `planned: operators` route with this route or an explicit reason, and the `operators` open-work key disappears. Platform, RLS, export, restore and admin conformance grow: an operator with memberships on two tenants and a pending invitation is erased, both tenants keep their revisions with the id and show a former team member, a second operator and another installation tenant are untouched, a live session of the erased operator reaches no tenant and is cleared on its next admin request, the operator's API keys on both tenants are revoked and counted, each tenant has one audit row of the erasure, a tenant left without an admin gets one back through the restore operation, the restore is refused on a tenant that has an admin, a later login with the old subject yields a new account without memberships, the register survives a restore of a backup from before the erasure, an archive of the operator's tenant expires, an archive of the older format with addresses in its actors imports without any, an export-import round trip keeps the attribution of current members and shows the erased operator as a former team member, and every stored actor after the migration or an import carries no address.
