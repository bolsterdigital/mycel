# ADR 035 - An operator account is erased by the installation; a stored actor carries an id, never an address

- **Status**: proposed
- **Date**: 2026-11-12
- **Refines**: ADR 009 rule 9 (attribution of every action) and ADR 018 (immutable revisions) for the operator address in a stored actor; ADR 019 rule 8 (every copy, backups) for operator accounts
- **Supersedes**: nothing; ADR 012 rule 4 and ADR 028 keep revisions and plans immutable, except for the one-time migration in rule 4 below
- **Preserves**: ADR 002 tenant isolation, ADR 017 (a tenant is one site), ADR 032 and ADR 034 for supporters and people

## Context

An operator is a human who works in the admin. The `operators` row (address, name, identity-provider issuer and subject, preferences) belongs to the installation, not to a tenant: one account can hold memberships on several sites, and a pending invitation is an `operators` row without a subject. `tenant.member.remove` removes one membership and keeps the account. No route removes the account itself, so the inventory of #169 D lists every operator copy as `planned: operators`.

Every write that records who acted stores the whole `Actor`, and the operator variant holds `operatorId` and `email`. That address therefore sits in current and historical revisions, bulk plans and their effects, form feed settings, connection intents, the outbox, `media.created_by` and `api_keys.created_by`. Revisions and plans are immutable (ADR 012 rule 4, ADR 028). It also sits in `erasures.actor` and `person_erasures.actor`, although migrations 0019 and 0050 and ADR 034 rule 2 say that column holds kind and id, never an address: the code stores `principal.actor` as it is. The admin shows a revision's author as that stored address; the audit view already resolves an id to a name and shows "a team member" for an unknown one.

The address in a stored actor is a copy, not the source: the id identifies the operator, and the account row holds the current address and name.

## Decision

1. **The installation erases an operator account, by explicit operator id.** Operator erasure is a platform operation (`platformOperations`, platform API and the `mycel` command line), not a tenant use case: the account is installation data, may serve several tenants, and no tenant may remove another tenant's member. A tenant's remedy stays `tenant.member.remove`. A request from the human goes to the installation maintainer, who runs the operation with the operator id; the system never derives an operator from an address, a name or an identity-provider subject. An id found neither in `operators` nor in the register of rule 2 is refused as a whole.
2. **An installation register makes the erasure durable.** Each request appends `(operator_id, erased_at)` to an append-only, installation-level register; a second request for a registered id is a no-op. The register holds no address and no name. It outlives every backup (ADR 019 rule 8): after a restore, the erasure step removes every registered operator again before the installation serves requests.
3. **Erasure removes the account and keeps the id as an inert reference.** It deletes the `operators` row (address, name, issuer and subject, a pending invitation included), every `tenant_memberships` row of that id, and the operator's preferences. Ids in revisions, plans, audit rows, API keys, media and registers remain: without the account they identify nobody. Every place that shows an actor resolves the id at read time; an absent or registered id shows as a former team member, localised, never as an address. The stateless session cookie needs no revocation: each admin request loads the account and its memberships by id, so a missing account is no session. The identity-provider account is outside Mycel and stays; a later login with the same subject finds no account and gets no access, and a new invitation creates a new operator id, never the old one. Erasure is not refused when it leaves a tenant without a `tenant:admin` member; the result lists those tenants so the maintainer can invite one.
4. **A stored actor carries kind and id, never an address.** Every write that persists an actor stores the operator variant as `{ kind: 'operator', operatorId }`; the address stays in the in-memory principal only, for the session. One migration removes `email` from every stored operator actor in long-lived copies (revisions, bulk plans and effects, form feed settings, connection intents, media, API keys, both erasure registers); this is the only in-place change to revisions and plans this ADR allows, it touches no other key, and it is a schema step that runs as the migration owner, not a grant to any role. Short-lived copies (outbox, presence) stop receiving the address and expire on their own term. Because no address is at rest, erasure has nothing to scrub in history; this also makes `erasures.actor` and `person_erasures.actor` what migrations 0019, 0050 and ADR 034 rule 2 already say they are.
5. **Exports and backups follow.** An export archive names members by address (`as-invitation` on import). Erasure expires every archive of a tenant where the operator held a membership, as supporter erasures do (ADR 032). A restore of a backup taken before the migration of rule 4 runs that migration before rule 2 re-applies the register. An import never creates an account for a registered id: a membership in an archive becomes an invitation by address, which is a new operator.
6. **Names in free text are not erased.** An operator named in prose, an API-key label, a connection purpose or a pattern name is not found from an operator id; the tenant edits current text through ordinary use cases, and the result of the operation says so rather than reporting "all erased" (as ADR 034 rule 6).

## Rejected alternatives

- A tenant use case `tenant.operator.erase`: one tenant would delete an account that other tenants rely on, or each tenant would erase only its own copy and the account would never go.
- Keeping the address in stored actors and scrubbing it on erasure only: needs an in-place update path on every immutable table for ever, and keeps addresses of living operators in history, exports and backups where the id already suffices.
- A tombstone row in `operators`: keeps a record that only says someone was there; an absent row with an inert id renders the same and holds nothing.
- Removing operator ids from revisions and plans: rewrites attribution structure for no privacy gain once the account is gone, and breaks the audit trail of ADR 009 rule 9.
- Refusing erasure of the last admin of a tenant: a legal erasure cannot wait for a tenant to appoint a successor; the maintainer can invite one.
- Deleting the identity-provider account from Mycel: the IdP is a separate system with its own owner (ADR 008); Mycel only stops recognising the subject.

## Consequences

A migration (number claimed at build) adds the operator register, removes `email` from stored operator actors in the long-lived copies named in rule 4, and gives the platform role what erasure needs on `operators`, `tenant_memberships` and preferences. The actor serialisation becomes one function in core that every persisting adapter uses, with a conformance test that no stored actor carries an address. `actorLabel` and the revision, presence and conflict views resolve an operator id to a name through the members list; an absent id gets the existing "a team member" wording. The operation joins `platformOperations`, the platform API and the command line; the restore drill re-applies the register. `STORAGE` replaces every `planned: operators` route with this route or an explicit reason, and the `operators` open-work key disappears. Platform, RLS, export, restore and admin conformance grow: an operator with memberships on two tenants and a pending invitation is erased, both tenants keep their revisions with the id and show a former team member, a second operator and another installation tenant are untouched, a later login with the old subject gets no access, the register survives a restore of a backup from before the erasure, an archive of the operator's tenant expires, and every stored actor after the migration carries no address.
