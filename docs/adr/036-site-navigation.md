# ADR 036 - Site navigation is a revisioned aggregate of menus and placements, published per locale

- **Status**: accepted
- **Date**: 2026-11-14
- **Builds on**: ADR 002 (RLS), ADR 007 (localisation), ADR 009 (HTML first, MCP), ADR 012 (content types, read route), ADR 014 (hostnames and paths), ADR 016 and 018 (access, capabilities, per-locale readiness, caching), ADR 026 and 027 (merge and base on save), ADR 030 (trash and references)
- **Supersedes**: nothing. The `navigation`, `legal`, `support` and `help` fields of the site chrome document (#11 E, migration 0026) are migrated by rule 10 and then retired; the free footer text, credits and branding stay where they are.

## Context

A tenant site today has one flat list of at most twelve links in its chrome document, a legal list and two single links, written straight to the live site by `site.chrome.update` with `content:write`. Every link is a typed URL, so a slug change breaks it, a menu label cannot inherit a page title, and there is no second level, no reuse between header and footer and no draft. The owner chose the visitor experience on 2026-10-31: a hybrid bar with the full menu as a panel from the right, at most two levels, at most two calls to action, the label chain "menu text, else featured title, else title", one layout, and draft, preview and explicit publish because a wrong menu changes every page at once. This ADR fixes the data, publication, reference and cache contract that those choices need. Presentation (the bar's auto-fit, the dialog, motion) is not decided here beyond what the contract forces.

## Decision

1. **One navigation document per tenant holds all menus and their placements.** It is an aggregate: `menus[]` (each with a stable `id`, an internal name and ordered `nodes`) and one `placements` object. Menus stay individually addressable in the admin, API and MCP, but every change to any menu or placement produces one new revision of the whole document. That makes a menu and the placement that shows it visible together, never in mixed generations, at the cost of a conflict when two editors change different menus at once; rule 4 keeps that conflict narrow. A menu is not a content item, has no block tree and is never stored as rich text.

2. **A node is a link or a group, and the tree has two levels.** A node has a stable `id` and is either a `link` with a `target`, an optional `label` (localised, per rule 6) and optional children, or a `group` with a required localised `label` and children but no target. Only top-level nodes may have children; a third level is refused, never flattened. A group renders as a disclosure, never as `href="#"`. Budgets are protective limits, validated in core: at most 20 menus, 100 nodes per menu and 500 per tenant. Duplicate node ids, unknown parents and cycles are refused.

3. **A target is a closed union.** `content(itemId, anchor?)` points at a `page` or `article` by id; `anchor` is a stable block id with a renderer contract, never a slug of a heading. `url(href)` is a site-relative path or an `https:` URL, with the same validation as today's chrome links, and opens in the same tab. `system(home | search)` is resolved by the platform: home is the locale's root, search is `searchPath(locale, defaultLocale)` from the site search (#42). Further kinds (sections, dossiers, campaigns with their own route, downloads, `mailto:`) need an amendment when their public route exists; a campaign is reached through its landing page (ADR 033 rule 2). A pasted URL that matches an internal item may be offered as a content target, but is never converted silently.

4. **Placements are a small closed set.** `main`: one menu, plus the ids of the top-level nodes that may appear in the bar; the whole menu always appears in the panel. `actions`: at most one menu with at most two nodes, in priority order; the first renders primary, the second secondary. `footer`: zero to four columns, each a menu plus an optional localised column title, all children visible. `legal`: at most one menu. Search and the language switch are platform utilities, not placements. The same menu may sit in several placements; there is no per-placement label or order override: a different footer means a different menu. The concurrency base of rule 7 covers the whole document, but the save path merges per menu and per placement field (ADR 026), so only edits to the same menu or the same placement conflict.

5. **Resolution chooses the target locale first, then the label inside that locale.** For a content target: tenant, item id and requested locale give one allowed published target projection, from the same publication list the sitemap and search use (#9, #42), never from drafts. Its URL comes from the current slug and the site's path rules (ADR 014), so a slug change follows without a menu edit. The label is the node's own label in that locale, else the published effective featured title, else the published title, in the same locale. No other source: no SEO title, no truncation, no new `navigationTitle` field. A missing target locale is a readiness problem shown in the editor; where the tenant's fallback setting (ADR 018 rule 9) allows another locale, the link points at that locale and carries its `hreflang`.

6. **A node's own label is localised and optional.** Clearing it returns the node to inheritance. A group's label is required in every locale the navigation is published in. Order and structure are the same in every locale; diverging per-locale menus are a later, explicit extension, not copies. Saving in one content language preserves the other languages' labels.

7. **Navigation has drafts, preview and explicit publication per locale.** Every save creates an immutable revision and carries `baseRevisionId` (ADR 018 rule 2, merge per ADR 026). Publication points one revision per locale; publishing validates the whole document as reachable in that locale and never publishes another locale. Writing, including restore, needs `content:write`; publishing and unpublishing a locale need `content:publish`, the same split as content (ADR 018 rule 5). Restore copies an older revision into a new draft, which needs publishing again. Agents use the same use cases through MCP with the same capabilities (ADR 009). The admin preview renders the draft navigation against published targets only; a preview of draft targets is an explicit authorised content preview, never implied.

8. **What visitors see when a target changes.** A target that is offline, trashed, in another tenant, restricted, unpublished in the locale or unknown is not rendered publicly: no dead link, no draft link, no fallback to home. A link node with children whose own target disappears keeps its children only when it has its own label in that locale, and then renders as a group; it never reads the offline title. Without its own label the whole branch disappears publicly, and the editor lists the children that became unreachable through this menu. Empty groups and empty menus render nothing. Restricted targets (ADR 016) are not resolvable publicly until the reader teaser projection (#19) defines what a menu may show; a menu never grants access. There is no personalised navigation, so an anonymous shell never caches session-dependent data.

9. **Menus are references.** Content targets register references next to the block references, with draft and published owners, checked in batch on save and publish and re-checked on public read. Moving an item to the trash or deleting it is refused while the current draft or a published revision of the navigation points at it, naming the menus (ADR 030 rule 4). Older revisions do not block deletion; restoring one marks the missing target and goes through readiness again. Deleting a menu is refused while a placement in the draft or a published revision uses it. Search-path and home targets have no reference. Lock order on publish is navigation before content, so publishing navigation and taking a target offline cannot interleave inconsistently.

10. **Migration is lossless and lands published.** The forward migration turns the existing `navigation` list into a menu placed in `main` with all top-level nodes in the bar, `legal` into a menu placed in `legal`, and `support` and `help` into a footer column; none becomes a call to action. Every existing label becomes an explicit own label in every locale it has; every URL stays a `url` target, and no URL is converted to a content target automatically. The migrated document is revision 1, published in every locale the site publishes. Exports from before the migration stay importable through the same mapping. `site.chrome.get` and `site.chrome.update` keep their names for footer text, credits and branding only; from the migration on, `site.chrome.update` refuses the retired fields, so the old setter can never bypass publication. The public layout stops reading `Object.values(label)[0]` as an implicit fallback.

11. **Caching hashes the resolved navigation, not only its revision.** The same navigation revision gives a different header after a target page republishes a title or slug. The public ETag therefore includes a digest of the resolved navigation for the locale (labels, URLs, presence of every node), next to the existing inputs. The next origin read sees new published metadata; a shared cache may serve the previous header for at most its freshness window, and an immediate purge is the job of the public cache and redirects work (#11, #9), not a promise of this ADR. Authorised previews stay `no-store`.

12. **The contract is HTML first.** All destinations are reachable without JavaScript: one server-rendered tree in `nav` landmarks with real anchors and native `details`/`summary` for groups and the panel. Enhancement upgrades that tree to a modal `dialog` and measured bar links; it never hides the fallback before it succeeds. Site navigation uses disclosures, never `role=menu` or `menubar`. Targets are at least 44 by 44 CSS pixels. These are construction rules for the public renderer (ADR 009); the measurable gates live in the frontend-quality contract.

## Examples

- **Slug change.** "Over ons" is a content target with no own label. The editor renames the page slug from `over` to `over-ons` and publishes: the next public read links to `/over-ons` with no menu edit. A redirect from `/over` is #9's job.
- **Inherited label.** The featured title of "Themes" changes in a draft: the live menu keeps the published text. On publishing the page, every inheriting node follows; a node with its own label "Thema's" does not.
- **Offline parent.** "Campaigns" links to a page and has three children. The page goes offline. With its own label "Campaigns" in nl, the nl menu shows a group with three children; in en, without an own label, the branch disappears publicly and the editor lists the three children as unreachable through the main menu in en.
- **Two editors.** One editor edits the footer menu while another reorders the main menu on the same base: both saves merge. Two editors reordering the main menu on the same base: the second gets a conflict.

## Rejected alternatives

- **Keeping the chrome document and adding fields**: no drafts, no references, and the existing setter writes live with `content:write`, which is the problem.
- **A revision per menu with its own publication**: a placement and a menu could go live in different generations; atomic publication would need a release engine. The aggregate with per-menu merge gets the same editing freedom without it.
- **Menus as content items or block trees**: a menu has no body, slug or read route; reusing the item lifecycle would add trash, scheduling and access rules that mean nothing for a menu.
- **A per-placement label override**: a third label source hidden on the placement; choosing or duplicating a menu is explicit.
- **Arbitrary nesting**: deep menus fail on phones and keyboards; the owner chose two levels.
- **Hashing only the navigation revision for the ETag**: stale titles and URLs after a page publication.

## Consequences

- Build follows the brief's steps: B (model, storage, references, resolver, registry, API, MCP, migration) is `flagship-review` because it adds a publication boundary and a migration; C (menu editor), D (public header, footer, panel) and E (search entry and the integrated test) are workhorse unless they change capabilities, CSP or access.
- A new migration adds the navigation table, its immutable revisions, per-locale publication pointers and navigation references, all with forced RLS (ADR 002), and moves the four chrome fields.
- Export and import carry the navigation document with all revisions and pointers; ids are kept, only the tenant changes, as for every other table.
- The public layout gets one batched navigation resolve per request, without N+1 reads or full bodies.
- Scheduled publication of navigation, a service bar, social icons, an announcement bar and per-locale menu structures are later decisions.
