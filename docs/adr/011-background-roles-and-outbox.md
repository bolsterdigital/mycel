# ADR 011 - Background work crosses tenants through a dedicated role and the outbox only

- **Status**: accepted
- **Date**: 2026-10-21
- **Amends**: ADR 002 (adds one role), ADR 008 (confirms the Postgres-table queue)
- **Amended**: 2026-10-21 by ADR 019 rule 6 (intent row plus provider idempotency key plus reconciliation before retry); 2026-10-21 for TODO #7 (rule 1: the identity tables and `mycel_auth`); 2026-10-22 at the review of PR #7 (rule 1: the fronts enter `mycel_auth` from the `mycel_authenticator` login, never from the operator connection); 2026-10-22 for TODO #14 (rule 1: `tenant_hostnames` is read the same way); 2026-10-22 for TODO #15 (consequences: `jobs` is the second queue under `mycel_worker`); 2026-10-22 for TODO #16 (rule 1: the platform role); 2026-10-22 for TODO #22C (consequences: `mail_sends` delivered, `readOutboxEvent`)

## Context

ADR 002 gives the application one role, `mycel_app`, which is bound by forced Row Level Security and sees exactly one tenant per transaction. The first vertical probe showed that one component legitimately needs to look across tenants: the outbox worker, which drains committed domain events and hands them to subscribers. Running it as `mycel_app` cannot work (no tenant context, zero rows); running it as the schema owner would bypass RLS on every table; granting `BYPASSRLS` needs a superuser and is just as broad.

## Decision

1. **Cross-tenant reads happen only on tables that are queues or logs for the platform itself**, today the `outbox` table. The one exception that is neither queue nor log is authentication: resolving an API key or an operator's memberships happens before a tenant context exists, so the identity tables (`operators`, `tenant_memberships`, `api_keys`) are read, and `operators` written, through the dedicated `mycel_auth` role under the discipline of rule 2 (migration 0007). The fronts enter `mycel_auth` from the `mycel_authenticator` login, a role with no rights of its own (`inherit false`) that can do nothing but `set local role mycel_auth`; web and API therefore never hold the schema owner's credentials, and the operator connection of rule 2 stays with migrations, the seed and the worker. The same route resolves the site being visited: `tenant_hostnames` (migration 0008, TODO #14) is read through `mycel_auth` before a tenant context exists, because the hostname is what establishes that context (ADR 002 rule 3, ADR 014 rule 1); `mycel_app` sees only its own tenant's hostnames. Platform operations (creating a tenant, setting its entitlements and status; ADR 002 rule 4, ADR 015 rule 4) run as `mycel_platform` (migration 0010, TODO #16), a role that may read and insert `tenants`, update their `entitlements` and `status`, and read and insert platform hostnames, and nothing else; the API enters it from the same `mycel_authenticator` login, so the platform API never holds the schema owner's credentials either. Tenant-scoped management of members and keys runs as `mycel_app` under RLS like any use case. Tenant data (pages, forms, submissions, events, supporters, ledger) is never read across tenants by application code; platform reports use per-tenant transactions or a separate read model.
2. **A dedicated role per cross-tenant job, with a policy scoped to that role and that table.** The first is `mycel_worker` (migration 0003): `select, update` on `outbox`, policy `worker_drain ... to mycel_worker using (true)`. The operator connection does `set local role mycel_worker` for the duration of one drain transaction and nothing else.
3. **Subscribers run inside a normal tenant-scoped unit of work.** The worker reads an event, then calls each subscriber with a `system` principal for the event's tenant. The supporter ingest therefore writes under RLS like any use case.
4. **Delivery is at-least-once per subscriber.** The outbox row records which subscribers handled the event (`delivered_to`), attempts are capped with exponential backoff, and claiming uses `FOR UPDATE SKIP LOCKED` so several workers can run. Subscribers must be idempotent: ingest dedups on the deterministic event id; mail subscribers will record a send key before the first attempt (follow-up, see consequences).
5. **The outbox is the only event transport.** No broker, no `LISTEN/NOTIFY` as a source of truth (ADR 008). Partitioning or archiving processed rows is an operational migration, not a model change.

## Rejected alternatives

- **`BYPASSRLS` on the operator role**: one flag, but it opens every table to the component that least needs it, and it requires superuser to grant on managed Postgres.
- **A tenant loop in the worker** (iterate tenants, drain each under RLS): correct but O(tenants) queries per tick and it needs a cross-tenant list of tenants anyway.
- **Delivering events synchronously in the use case's transaction**: no worker, but a failing mail provider would roll back a signup, and the supporter module would be coupled to every publisher.

## Consequences

- Every new cross-tenant job (dunning scheduler, campaign sender, reconciliation) gets its own role and policy, or reuses `mycel_worker` only if it touches the same queue table.
- Since 2026-10-22 (TODO #15, migration 0009) `jobs` is the second queue under `mycel_worker`, with the same discipline: `mycel_app` inserts under its own tenant and reads nothing, the worker claims with `SKIP LOCKED` (as a five-minute lease, the handler running outside the claim transaction), tenant jobs run under a `system` principal as in rule 3, and platform jobs enter their own role per transaction (`mycel_janitor` for the rate-limit sweep). The RLS conformance test (TODO) asserts that every policy with `using (true)` is bound to a named worker role, never to `public` or `mycel_app`.
- Transactional mail sent from a subscriber must become idempotent before production: a `mail_sends` table keyed by `(event_id, subscriber)` written before the provider call. Delivered: migration 0006, and since 2026-10-22 (TODO #22C, migration 0013) an exclusive claim plus the `mail.reconcile` job (`docs/reference/mail.md`).
- Since 2026-10-22 (TODO #22C) the outbox has a second reader under rule 1: `readOutboxEvent` loads one event as `mycel_worker` for the `mail.reconcile` job, which uses it only when its tenant is the job's tenant.
- The `events` table partitioning promised in ADR 003 is still owed; it interacts with the `(tenant_id, id)` primary key used for dedup and gets its own migration and test.
