# ADR 022 - Managed extensions and site integrations

- **Status**: accepted
- **Date**: 2026-10-24
- **Supersedes**: ADR 004 rule 4 only where it forbids all tenant-specific code; ADR 013 rule 5 and its absolute ban on operator-managed packages and scripts; ADR 020's rejection of per-tenant layout code only where it would also reject bounded managed style extensions
- **Preserves**: the validated block tree, framework-free core, one edition, HTML-first rendering, tenant isolation and accessible bounded layouts (ADRs 001, 004, 009, 013, 015, 020)

## Context

Validated configuration should remain the default, but a particular site can need a block, visual treatment, content presentation or external widget that will never be a general product feature. Requiring every such change to enter the common product makes legitimate site work impossible or drives it into invisible CSS and scripts. Installation, availability, activation, asset delivery and execution have different boundaries and must be named separately.

## Decision

1. **Configuration is the first route, managed extensions are a supported route.** A platform maintainer with deployment authority may install a reviewed extension package for selected tenants, pages or defined groups without upstreaming it or activating it for everyone. Tenant operators may configure only admitted and installed packages within their granted capabilities; `tenant:admin` alone never grants package installation or server deployment. A tenant editor cannot upload arbitrary CSS, JavaScript, templates or backend code. An extension is not a per-tenant fork or a second product edition; the same architecture is available to self-hosters.
2. **Every managed package has a versioned manifest and an owner.** The manifest identifies package/version, supported core API and schema versions, dependencies, owner and maintenance contact, capabilities, activation scope, admin field schemas, block rendering and supported layout widths or parts/slots, locales, preview behavior, search/indexing and export behavior, fallback behavior, migrations, compatibility tests and a deprecation path. Installation refuses incompatible contracts. Deactivation stops new authoring or execution in its scope but cannot make previously valid stored blocks unreadable or silently remove them from export; migration, retained rendering or an explicit fallback must preserve historical content. Truly unknown types remain invalid on new writes. Exact package and registry APIs are deferred until a concrete extension proves them; this is the required contract, not a claim that an SDK exists.
3. **Choose the smallest content model that carries the semantics.** A registered block or variant fits content inside an existing page or article. A type profile adds validated metadata, editorial presentation and listings to `page` or `article` without silently creating a third storage or publication lifecycle. A genuinely new domain entity, lifecycle, permission or access rule requires a new ADR. A profile's type identity, readiness, access, teaser, locale, revision and publication rules apply consistently in HTML, JSON, MCP, feeds, search and export; no representation may leak a draft or bypass access.
4. **Effective style is inspectable.** Theme values, managed style extensions and scoped overrides resolve to one effective model. The admin and preview show each value's source, locked settings and the real public result. Extensions use a versioned style API with declared properties, parts and slots and bounded widths. Hidden `!important` overrides and a free CSS field are not the supported customization contract. Changes are validated for contrast, responsive behavior and accessibility.
5. **Selective loading is not isolation.** A package can be installed without activation, activated for selected sites or pages, and send browser assets only where used; server code shipped in the same process remains trusted code with the process's privileges. `packages/core` stays framework-free, imports no runtime extension package or I/O library, and exposes typed ports and validated contracts to adapters. Trusted in-process code is co-released and compatibility-tested with the host. Arbitrary or untrusted backend execution belongs in an external service or dedicated deployment, with an authenticated API and an explicit owner. Package placement or limited activation makes no promise of proprietary in-process licensing; ADR 006 and applicable AGPL obligations still govern the actual integration.
6. **Site integrations are registered, not pasted into content.** A managed CMP, tag manager or similar script declares provider/container, owner, route allowlist, consent categories, network destinations, review record and kill switch. It never runs in admin or editorial preview. Sensitive public routes, including payment, donor self-service, magic links and authenticated reader areas, require explicit route review or exclusion. CSP constrains loading but does not make a permitted tag manager safe: whoever can publish arbitrary tags may read accessible page data. Consent defaults and choices must be handled before tags execute; privacy, performance and accessibility acceptance are per site, so Mycel cannot make a blanket no-cookies or fixed-budget claim when these integrations are enabled.
7. **Embeds have a bounded public contract.** An external stream or widget uses a registered block, separate origin when available, a constrained message interface, permission and consent review, responsive size and a meaningful no-JavaScript or unavailable-provider fallback. It cannot silently acquire admin origin privileges. A widget may require JavaScript without making the host page or core form flow depend on it.

## Rejected alternatives

- **Every bespoke block must become a general product feature**: one legitimate use is enough; forcing general activation creates unnecessary product obligations.
- **A free CSS/script field or unrestricted plugin upload**: it hides the effective site design and gives unreviewed code the page or server's privileges.
- **Calling selective assets a sandbox**: conditional downloads do not isolate in-process backend code or a permitted tag manager.
- **A general canvas or workflow runtime**: it would replace the bounded block, style and use-case contracts before their real extension seams are known.

## Consequences

- The first implementation must prove one managed block/style package and one bounded embed against the manifest, locale, access, preview, export, responsive and fallback contracts. It should not invent a marketplace or speculative runtime SDK.
- Extension compatibility, asset selection and style provenance need conformance fixtures; site integration gates need public route, consent, CSP, a11y and performance tests. Existing implementation is not assumed to provide them.
- Site-specific availability is an activation decision, not a source-visibility or licence exception. A new business semantic gets its own ADR before implementation.
