# ADR 033 - A campaign is a participation entity with one landing page and referencing cards

- **Status**: accepted
- **Date**: 2026-11-12
- **Builds on**: ADR 003 and 019 (supporter events, stable id, erasure), ADR 005 and 024 (ledger, external ownership), ADR 012 and 022 (two stored content types, type profiles), ADR 016 and 018 (access, per-locale publication, capabilities), ADR 023 (versioned forms and actions), ADR 030 (trash), ADR 032 (erasure lifecycle)
- **Supersedes**: nothing. `page` and `article` remain the only stored content types.

## Context

Campaign sites need a petition, a signup action and later a fundraiser as recognisable items: an editor makes one, publishes its own landing page and places the same campaign as a card on other pages and articles. The predecessor registered a custom post type per kind with its own template and a card that re-read the post; that live reference is the behaviour to keep, the post types and templates are not. Mycel today has a `form` block, form kinds `petition` and `signup` with a content-hash version, and a declared but unused `petition.signed` supporter event. It has no campaign entity, no participation state, no counter and no reference block for a whole item. ADR 022 rule 3 requires an ADR for a new domain entity and lifecycle. The word campaign is also used for a mailing send (ADR 010 rule 6, ADR 012 rule 5); the two must not merge.

## Decision

1. **A campaign is a tenant-owned domain entity, not a third content type.** A `campaigns` row holds `id`, `kind` (`petition | signup | fundraiser`), `landingItemId`, `formId`, `participation`, `goal`, `archivedAt` and `updatedAt`. It holds no title, slug, lead, image or body. The landing item is a `page` (ADR 012) and is the only source of everything an editor writes and a visitor reads: the localised title, lead, featured image, block tree, slug and SEO of its published revision. One campaign has exactly one landing page and a page is the landing page of at most one campaign (unique constraint). The admin shows campaigns as their own kind of content with their own list, filters and creation flow; that is a presentation over the page plus the campaign row, in the sense of an ADR 022 type profile, and it adds no storage or publication lifecycle.

2. **The landing page owns publication; the campaign owns participation.** Visibility, per-locale readiness, scheduling with a pinned revision, unpublishing and the trash are exactly the page's (ADR 018, 030). There is no campaign read route and no second slug: the page URL per locale is canonical, and share links, thank-you state and cards point to it. Participation is separate: `participation: { state: draft | open | closed, opensAt?, closesAt? }`. A campaign accepts participation only when its state is `open`, the current time is inside the window (evaluated at the moment of use, ADR 019 rule 4), it is not archived, and its landing page is published and public in the submitting locale. Publishing the page never opens participation and opening never publishes the page. A closed campaign with a published page shows its result and no active submit.

3. **The server decides at submit time, whatever the HTML said.** A form bound to a campaign belongs to that campaign only (unique `formId`); wherever it is rendered, the submit use case re-reads the campaign's participation inside the submission transaction and refuses with the typed error `campaign.closed` when rule 2 does not hold. A cached or stale open page, a reposted form or an old tab therefore cannot add a participation after closing. The form keeps its own kind, which must match the campaign (`petition` with `petition`, `signup` with `signup`); a fundraiser binds a donation form once ADR 005 is built.

4. **A card is a reference, never a copy.** A `campaign-card` block stores `campaignId`, `variant: compact | full` and the existing block `width`, and records a `campaign` reference. It resolves at render time from one public campaign projection: the landing page's currently published revision in the requested locale, the participation state and the public counter. It does not follow the host page's revision pin: a scheduled host page shows whatever the campaign publishes when it is read, and the editor states that the card is live. Publishing a host page never publishes the landing page or opens the campaign. Compact shows title, lead, featured image, progress when the goal is public, and a link to the landing page. Full may also render the campaign's form, only while participation is open; otherwise it renders as compact with the result. A missing, archived, trashed, other-tenant, draft, unpublished-in-this-locale or non-public target renders nothing publicly, never a broken call to action; the editor and authorised preview show why. Selection in the editor searches only the tenant's own campaigns.

5. **A landing page bound to a campaign is public.** Restricting its access (ADR 016) is refused while it is bound. Members-only participation is a later decision with its own ADR, because counter, card and teaser would each need an access rule.

6. **Caching follows the projections the response used.** The ETag of a page that renders a card includes the landing page's published revision, the locale, the participation state and the counter value it showed. A response that renders a form stays `no-store`, as every form page does today. Rule 3 makes cache staleness a display delay, never a participation right.

7. **Participation is a confirmed, deduplicated fact per supporter.** A submission counts for a campaign once it is confirmed by the designated confirmation owner (ADR 023 rule 6, ADR 024 rule 5); a pending double opt-in does not count. The campaign domain keeps one `campaign_participations` row per `(campaign, supporter id)` with the confirming submission, confirmation time and an optional withdrawal time. Reposting, a second confirmation or a second submission by the same supporter changes nothing; withdrawing sets the withdrawal time; signing again after withdrawal clears it. On confirmation the supporter log receives `petition.signed` for a petition, or `form.submitted` for a signup, carrying `campaignId` as an additive field of the existing envelope. A signature is not mail consent: newsletter consent arises only from an explicit consent field, as today, and stays a separate fact.

8. **The counter is a rebuildable aggregate with a fixed unit.** Petition: confirmed, non-withdrawn signatures. Signup: confirmed, non-withdrawn signups. Fundraiser: the sum of verified paid amounts in minor units of the tenant currency, from the ledger or verified external evidence only, minus refunds and charge-backs; a started checkout is not money, and an externally owned subscription never causes a second charge (ADR 005, 024 rule 7). Goal target and milestones are data in the unit of the kind. Erasure (ADR 019 rule 8, ADR 032) deletes the erased supporter's participation rows and, in the same transaction, adds those that were confirmed and not withdrawn to an anonymous per-campaign `erasedCount` that holds no identifier. The public count is the active participation rows plus `erasedCount`, so an erasure never lowers it and a rebuild from the remaining rows gives the same number. An erased person who signs again after readmission (ADR 032) is a new supporter and counts again; that is the accepted cost of keeping no identifier. The public projection exposes only aggregates, never names or a participant list, and a tenant may hide the counter.

9. **Nothing cascades over participation or money.** A campaign is not deleted: it is archived, which closes participation and removes it from card selection, and therefore needs publish rights (rule 10). Archiving is refused while a published revision of another item holds a card for it, naming those items, as ADR 030 rule 4 does for items. Trashing the landing page is refused while it is bound to a campaign that is not archived. Revisions, submissions, participations and ledger entries are never removed by archiving, unpublishing or trashing. Duplicating a campaign creates a new campaign, a new landing page with fresh ids and a new form, and a counter that starts at zero.

10. **Every surface uses the same operations and existing capabilities.** `campaign.create` and `campaign.update` (carrying `baseUpdatedAt`, ADR 027) require `content:write`, plus `forms:write` when they bind or create a form. Every operation that changes participation state or its window changes the public effect and requires `content:publish` as well, as ADR 030 rule 6 does for delete: `campaign.open`, `campaign.close`, `campaign.archive` (which closes participation, rule 9) and a `campaign.update` that changes `participation.opensAt` or `participation.closesAt` (moving `closesAt` into the past closes, moving it out reopens). The check compares the stored and the requested window inside the update transaction, so a write-only principal can edit everything else but gets a typed refusal for the window. Reading participants requires `supporters:read`; exporting them follows the supporter export capability; fundraiser money operations use the `donations:*` and `money:refund` capabilities. UI, HTTP and MCP call the same use cases (ADR 009). A reference to another tenant's campaign is refused on save like any unknown reference.

11. **Export and import carry campaigns whole.** Campaigns, participations and `erasedCount` are exported with the tenant; import restores campaign, page, form, media and supporter ids as exported into the new tenant (only the tenant changes, like every other table), so the references between them stay intact. Participations are personal data under the supporter export and erasure rules.

12. **Terminology.** In code, the API and the admin, a bare `campaign` is this entity, in the `campaigns` module. A mailing send is a mailing edition; the existing field `delivery.email.campaignId` (ADR 012 rule 5) keeps its name and refers to a mailing send. Events (dates, place, RSVP) stay their own domain; reusing the card's presentation for them later needs its own decision.

## Examples

- **Petition.** An editor creates a petition: Mycel creates a draft page, a petition form and the campaign row in `draft`. The editor writes the page, publishes it in nl and en and opens participation. A visitor signs in nl and confirms; the counter becomes 1. Signing again with the same address changes nothing. The petition closes on its `closesAt`; a tab opened before that posts the form and gets `campaign.closed`, and the page shows the final count.
- **Signup.** A signup with a consent field: a confirmed signup counts once and, because the visitor ticked consent, also subscribes the list. A visitor who does not tick it counts and receives no mail beyond the confirmation.
- **Fundraiser (after ADR 005 is built).** The counter shows paid euros; an open checkout is not shown; a refund lowers the total.

## Rejected alternatives

- **A third stored content type `campaign`**: duplicates revisions, per-locale publication, scheduling, trash and the read route, which ADR 012 and 022 deliberately keep in two types.
- **Campaign copy on the campaign row next to the page**: two sources for one title, which drift; the card would show text the landing page does not.
- **A card that snapshots the campaign at host publish time**: the counter and closing would be wrong on every older page, and an unpublished campaign would stay visible.
- **Open participation implied by publication**: an editor checking a page in production would start collecting signatures and sending mail.
- **Counting submissions instead of supporters**: reposts and unconfirmed addresses inflate the number.
- **Keeping erased participations with a hash for dedup**: a lasting identifier for an erased person; an anonymous count suffices.

## Consequences

- New tables `campaigns` and `campaign_participations` with RLS, a migration claimed at build time, a `campaign` reference kind and a `campaign-card` block with schema version 1. `content_block_refs` gains a caller that refuses archive and landing-page trash.
- The form submit path gains the participation check of rule 3 and the participation write of rule 7; existing forms without a campaign behave as before.
- The ordinary public page path resolves the campaign projection and folds it into the ETag; feeds, search, Markdown and `llms.txt` render a card as a link with title and lead only, never a form.
- Building petitions and signups (with card, admin and the complete flow), and later the fundraiser, are separate deliveries. This decision builds nothing.

## Amendments

- **2026-11-12, rule 11 (#47 B2):** the first text said import "remaps" ids. The importer keeps every id as exported and rewrites only the tenant (`IMPORT_RULE` in `packages/db/src/portability/import.ts`, `as-exported` for `campaigns` and `campaign_participations`); the wording now says that. The decision itself, references intact across export and import, is unchanged.
