# ADR 020 - Editing surfaces, stable block identity and revisioned operations

- **Status**: accepted
- **Date**: 2026-10-22
- **Supersedes**: ADR 012 rule 6 only (rich-text vocabulary and editor contract); the rest of ADR 012 remains in force
- **Refines**: ADR 004 rules 1 to 3 and 6 (block identity, heading context, rendering and references)
- **Builds on**: ADR 007 (localisation), ADR 009 (HTML first and one registry), ADR 013 (bounded customisation), ADR 018 (revisions, capabilities and publication)
- **Managed extension scope**: 2026-10-24 [ADR 022](022-managed-extensions-and-site-integrations.md) allows reviewed style parts, slots and type profiles within the same bounded block tree. The free canvas and arbitrary layout code rejected below remain rejected.
- **Rule 5 refined**: 2026-10-30. "Forms per block" is a fieldset per block inside one document form: the document's fields and every block's fields are saved together as one `content.item.update`, and every block action (insert, move, remove) is a button of that form that saves what was typed first and then runs its own operation of rule 6. Separate forms lost what was typed in one block when another was moved or inserted (editor trial of 2026-10-28). The model, the operations and their authorization are unchanged.
- **Rule 9 refined**: 2026-11-01. Pasted plain text is read as CommonMark by `markdown-it` with HTML off, and the result takes the same conversion path as pasted HTML. Core `fromMarkdown` stays the grammar of the block forms and the assist worker, where the round trip must be lossless. It is not a reader for text written elsewhere: it has no quote or image, and it treats every `_` and `**` as a toggle, so `snake_case_name` would lose its underscores. Both readers end in the same schema, so a difference between them can change how a paste is interpreted but cannot store anything the schema refuses.

## Context

An article needs a continuous writing surface, while a campaign page needs structured block forms. Neither interface should become the storage format. ADR 012 rule 6 excluded headings from rich text and included blockquotes; the editorial decision is now to keep section headings in the prose and give quotations their own structured cards. Before revisioned content is built, block identity and mutation semantics must also be fixed so that editors and agents never depend on shifting array positions.

## Decision

1. **The ordered block tree remains the stored document.** Every block has a stable string `id`, unique across the entire document including nested block lists, alongside its type, schema version and validated props. Arrays determine order; ids determine identity. Ordinary edits and moves preserve ids. New blocks get new ids; conversion of existing documents assigns ids once and preserves them thereafter. A document contains at most 200 blocks in total. ProseMirror text nodes are not separate blocks for this limit. Unknown block types or props remain invalid (ADR 004); the editor cannot introduce a second storage model.

2. **Rich text contains prose and relative section headings, never cards.** Its fixed, versioned ProseMirror schema permits `doc`, `paragraph`, `text`, `heading`, `bullet_list`, `ordered_list`, `list_item` and `hard_break`, with bold, italic, link, code and footnote-reference marks. Heading levels are relative section depths 1 to 3, not stored HTML tag names. The renderer resolves them against the enclosing block's semantic section depth to h2 through h4 (ADR 004 rule 3); h1 belongs to the document title. The schema and renderer must agree on valid nesting: a context that cannot represent a relative level within that range is invalid, not silently clamped. No blockquote, image, embed or raw HTML node is stored inside rich text. Zod validates allowed nesting, attributes, safe links and bounded tree size and depth on every write; the core does not import the editor.

3. **A quotation, image or embed is a typed block with its own fields.** A `quote` has `text`, structured `attribution: { name, role, source, url }` and variant `blockquote | pullquote`. An `image` references media by id and carries alt text or an explicit `decorative` choice, caption, credit and a validated layout/variant, including `float-left | float-right`. Localisable fields follow ADR 007. Embeds likewise use a registered block schema. Floats are renderer behaviour: data order stays reading order, and a narrow layout shows the image in that order. There is no tenant CSS or arbitrary layout escape hatch (ADR 013).

4. **There are no adjacent `rich-text` blocks in any sibling block list.** Core validation rejects a non-canonical tree. Editors and block operations normalise text before submitting a save, retaining the first block's id and concatenating prose in order without dropping marks, attributes or locale content. If a merge cannot preserve the data unambiguously, the operation fails rather than discarding it. Splitting retains the original id on the first part and assigns a new id to the second. Splitting prose to insert a card is one atomic split-and-insert operation at a paragraph boundary; a standalone split cannot commit forbidden adjacent text blocks. Removing or moving a card normalises any text newly brought together. Mutation results explicitly identify created ids and retired ids, including which surviving id receives merged text, so callers can update selections and references. No operation rewrites old revisions.

5. **Articles and pages edit the same model through different surfaces.** The enhanced article editor presents one continuous TipTap/ProseMirror document, with non-text blocks represented as atom cards with structured fields; saving converts it back to the block tree. Pages use forms per block plus preview and click-to-edit enhancement. Only the open-source editor core is used, without Pro, AI or cloud extensions; dependency admission remains subject to ADR 008. The conversion must round-trip every valid block example without changing ids, props, variants, locale values or text structure. Editing one locale preserves the others. Native forms without JavaScript edit this same model losslessly, including structured cards and block movement; there is no plain-text fallback that destroys unsupported content. Both surfaces pass the same accessibility gate (ADR 009).

6. **Small block edits are revisioned core use cases.** Alongside whole-document `content.item.update`, the shared registry exposes insert (before/after an id or at the start/end of a block list), move, remove, setProps and split-and-insert. Targets, placement anchors and enclosing blocks are addressed by id, never by array index; property patches cannot change block identity. Each mutation requires `content:write` and `baseRevisionId`, uses the same item lock, validation and tenant boundary as whole-document update, and atomically creates one attributed revision. A stale base returns typed `conflict` with no partial write (ADR 018). These are the operations used by no-JS form actions, keyboard commands and MCP; there is no separate agent API. Writing never grants publishing or sending rights, moves a publication pointer or changes a scheduled pin. Per-locale readiness, explicit teasers and immutable sent editions stay as defined in ADR 018.

7. **Block discovery and live references are tenant-scoped read models.** `content.item.find` supports block-type and reference filters with pagination and editorial read authorization. PostgreSQL handles these queries: suitable JSON containment queries use a GIN `jsonb_path_ops` index, and a derived `content_block_refs (tenant_id, item_id, revision_id, block_id, type, ref_id)` records structured references transactionally with revision saves and backfill. Live usage follows the explicit per-locale publication pointers, not the latest draft or every historical revision. Reference lookup and deletion checks enforce tenant ownership and ADR 004 rule 6; anonymous queries never expose draft references. This is not full-text search and does not authorise a second datastore. ADR 008 stays Postgres-first; an optional search adapter requires measured need under that policy.

8. **Preview uses the real renderer with explicit resolved data.** Rendering is a pure function of blocks, theme, locale and supplied resolver data; it performs no database access. The caller authorises the selected revision and resolves dynamic references under the same tenant and access rules before rendering. A saved preview works without JavaScript in a separate tab; an enhanced live preview may render an unsaved, validated draft through an authenticated endpoint in an iframe. Neither route publishes content or enters shared public caches. The public renderer continues to receive only the authorised locale/publication/access projection, never a whole snapshot containing unpublished translations (ADR 018). The editor can also show the anonymous teaser projection before publication.

9. **Paste and import are conversions into the schema, not storage shortcuts.** HTML is parsed against the permitted vocabulary: h1 becomes a first-level relative heading (h2 in root context), blockquote becomes a quote card, and images become image cards requiring media handling and alt/decorative input. Unsupported formatting is removed rather than saved as HTML. Recognised Markdown follows the same conversion path. File import starts with deterministic extraction; any later interpretation proposal is validated and reviewed before saving. Editor conversion of already valid content is lossless; importing unsupported source formats cannot make that promise and must let the editor inspect the result. AI assistance and remote MCP authorization are separate contracts, not introduced here.

## Rejected alternatives

- **A free canvas or per-tenant layout code**: makes the editing interface the design system and defeats ADR 013's bounded, testable variants.
- **An editor document or HTML as page storage**: couples every renderer and agent to editor internals or markup parsing. ProseMirror remains the constrained format inside rich text, not the page contract.
- **Array-index patches as the mutation API**: insertion or movement changes subsequent addresses. Stable ids identify the intended block; `baseRevisionId` still detects concurrent edits rather than pretending ids alone solve conflicts.
- **A separate agent API**: gives MCP different validation or capabilities and duplicates the human editing operations, contrary to ADR 009.
- **A text-only no-JS editor**: silently loses cards, marks or translations on save, so progressive enhancement would change the meaning of the stored document.

## Consequences

- Delivery proceeds through model/schema and id migration, then block operations and reference discovery, then the remaining block set/theme, then public rendering and finally the editing UI. This ADR specifies the contract; it does not claim those features are implemented.
- Core invariants cover id uniqueness and preservation, the block limit, permitted rich text, lossless normalisation and atomic split-and-insert. Registry/HTTP/MCP conformance covers shared authorization; database conformance covers revision conflicts, tenant isolation and draft/live reference separation. Editor conformance round-trips all block examples, including multiple locales; renderer conformance checks relative heading context, reading order and access across representations. No new executable suite is needed for this docs-only decision; these gates grow with their respective implementations.
- Existing documents need versioned conversion before use under the new schema. Historical ADR 012 rule 6 stays readable with a successor reference; it is superseded by this decision.
