# Mycel handoff pilot on one Mac

This local process supervisor follows the existing `mbp` handoff, with one fresh Codex thread per execution, independent review, merge and, when the shared drift threshold fires, audit. It does not schedule the entire roadmap. The current sample allowlist contains only `#44`: the current mbp queue does not offer two small, already briefed, startable items. `#44` is a substantial CMS shell task; completion of it would be a smaller pilot, not evidence of two completed items.

The supervisor is deliberately disarmed until its own code and permissions have passed independent flagship review. It uses `codex exec --approve-for-me` with the code repository and private planning sibling. The installed Codex CLI rejects combining that flag with `--sandbox`; the preflight child uses the same launch flags and structured output mode as an actual launch. It never disables signing, approval review, CI or branch protection. An automatic approval rejection stops the session. The [Codex non-interactive mode documentation](https://learn.chatgpt.com/docs/non-interactive-mode) describes fresh `codex exec` threads, JSONL events and the structured final result. The installed CLI must also support `gh pr merge --match-head-commit`.

## Operate

```sh
node tools/handoff-pilot/cli.mjs dry-run tools/handoff-pilot/pilot.example.json
node tools/handoff-pilot/cli.mjs preflight tools/handoff-pilot/pilot.example.json
node tools/handoff-pilot/cli.mjs start tools/handoff-pilot/pilot.example.json
node tools/handoff-pilot/cli.mjs status
node tools/handoff-pilot/cli.mjs logs
node tools/handoff-pilot/cli.mjs logs --files
node tools/handoff-pilot/cli.mjs pause
node tools/handoff-pilot/cli.mjs resume
node tools/handoff-pilot/cli.mjs stop
```

`dry-run` reads Git, GitHub, model profile and planning without writing files or starting agents. `preflight` checks CLI login, GitHub push rights, published planning and tool availability, then starts one bounded child per distinct model with the launch flags and JSON output schema. Each child runs `child-probe.mjs`: it takes and releases the planning Git index lock with `update-index --refresh`, opens and closes a `127.0.0.1` listener, runs `select 1` through `APP_DATABASE_URL`, and checks installed dependencies with `npm ls --depth=0`. The child requests the ordinary on-request approval route for that exact fixed probe, because the default workspace-write sandbox can deny local network operations. The automatic approval reviewer and configured sandbox remain in place; a rejected request ends the probe without retry or bypass and reports failed axes. A probe that merely returns negative axes with exit code zero is still a failure. The runner checks all four structured evidence fields and names a failed axis; no `preflight.json` is kept on failure. The probe makes no commit, install or repository content change. It proves these local child capabilities at that time. It does not prove third-party network access beyond any npm dependency check, GitHub push ability from inside the child, or future availability. If `commit.gpgsign=true`, the parent also runs a 15-second real `git commit-tree -S` probe without changing refs; a Touch ID requirement that cannot complete unattended is a stop. The probes are outside the bounded development chain and their output stays in the local state directory. A `start` requires a clean `main`, no existing claim or open PR on the allowlist and a preflight for the exact runner code and current head. The sample limit is eight chain sessions, two repairs per item and six hours. Stop kills the active agent process group; pause lets it finish but prevents the next launch. An interrupted session without a verifiable technical result blocks, rather than repeating a merge.

When CI turns red or another product issue blocks progress without a scope, process or limit danger, inspect `status` and `logs` and let the child publish its normal `blocked` result or reach its own limit. A `pause` prevents a subsequent launch while the current child finishes and still enforces the deadline. Use `stop` for scope or process danger, a hard limit, or a child that remains alive for 10 minutes after its terminal planning commit is visible on `origin/main` without writing its structured result and `turn.completed` event. Start that 10-minute clock from the observed remote commit, not from the child's status message. Preserve the status and logs before stopping; `stop` deliberately records `operator-stop` rather than inventing the child's technical outcome.

`MYCEL_PILOT_HOME` overrides the state and log directory, defaulting to `~/Library/Application Support/mycel-handoff-pilot`. `MYCEL_PILOT_PLANNING` overrides the sibling planning path. State, JSONL, stderr and structured results stay there with owner-only permissions, outside both Git repositories. Archive that directory before starting a new pilot. Status shows phase, item, model, PR, elapsed minutes, next action or stop reason and the number of recorded deviations. `logs` prints recent raw local events; review them for sensitive information before sharing. `pause` waits for supervisor acknowledgment and keeps the deadline monitor active for a running agent. At stop or deadline, the supervisor sends TERM, then KILL if needed, and verifies that no live process remains in the launched process group before releasing the lane. If a launch was reserved when the supervisor vanished, `stop` reports the uncertainty instead of claiming success.

The preflight requires `claude-notify` on the Mac, or a single executable path in the optional `notifyCommand` config field. It does not send a test push. A real `blocked` result sends one actionable phone push naming the run and stop reason; `complete` uses `CLAUDE_NOTIFY_BANNER_ONLY=1` for a local banner. Pause, stop and automatic approval events send nothing from the runner. The supervisor records a notification attempt in state before calling the helper and never retries it, so a crash at that point can lose a notice. `status` reports `invoked`, `failed` or `unconfirmed`; `invoked` means the helper exited successfully, not that the phone received it. A failed invocation also writes a `*-notification.stderr.log` file under `MYCEL_PILOT_HOME`. Inspect status and logs before beginning another bounded run. A custom notification executable must honor `CLAUDE_NOTIFY_BANNER_ONLY` to keep completion off the phone.

## Activation record

After independent flagship review and merge of the runner PR, create `activation.json` in `MYCEL_PILOT_HOME` with `outcome`, `runnerPr`, `approvedHeadSha`, `mergedSha`, `codeDigest`, `authorSessionId`, `reviewSessionId`, `reviewRecord` and `planningCommit`. `reviewRecord` is a path beneath `reference/` in private planning. The record must name the exact approved runner head and review session. `codeDigest` is the SHA-256 over `cli.mjs`, `child-probe.mjs`, `state.mjs` and `result.schema.json` in that order. The runner verifies the published review record, distinct sessions, four green CI jobs and GitHub's merged PR. A later `main` commit is allowed only when it descends from the approved runner merge, matches `origin/main`, and its runner files have exactly the digest of that approved merge. Run preflight on the current `main` _after_ its latest merge; the preflight must name that exact head and digest. Keep the review record in private planning and do not treat a local activation file alone as approval.

## Evidence and recovery

Each agent returns a schema-checked technical result with run and reserved session IDs, item, lane, phase, PR, head SHA, planning commit, outcome and evaluation observations. The supervisor additionally reads the actual Codex thread ID from JSONL. Before every next launch it checks GitHub's PR/head/merge/CI state, published planning and the normal mbp handoff. Review approval is pinned to the PR head; a changed head sends work back for independent review. Merge uses `--match-head-commit`. After merge, the published housekeeping commit must touch TODO, done register, drift log and the next handoff; the drift log must name the PR. At a drift threshold the merge session registers the shared task, then a separate audit session claims it atomically before working. If dev owns the task, mbp proceeds with its own lane.

`reviewRecord` in a review result is a `reference/*.md` path relative to the private planning repository. The structured output schema rejects absolute paths before the supervisor evaluates an approval. The review file must already be published and contain the exact PR head.

On crash, `resume` inspects the saved reservation and child process. If the child finished, it validates the saved result against GitHub and Git before advancing. It never replays an already verified merge. A reservation with no result, invalid handoff, stale approval or exhausted limit blocks and needs manual inspection of `status`, logs and external systems before a new run. Do not edit state to force a transition. Use a new bounded pilot after repairing the cause and preserving the previous logs. `stop` ends a run permanently.

After merge or audit, the verifier checks the next handoff against the next allowlisted item's tier. When the allowlist is exhausted, the ordinary repo handoff may point to a different tier; the completed item's tier is no longer a valid requirement for that handoff.

## Evaluation

Every session reports deviations with expected criterion, observation, detection, repair, suspected cause, prevention address and evidence. These are persisted alongside immutable session events but have no authority to pass a gate. During and after the pilot, reconcile these observations against [the evaluation brief](../../docs/plans/briefs/handoff-pilot-evaluation.md): whether the cause belongs in a planning brief, an existing conformance test, review criteria, a skill or runner infrastructure. Record the actual edit and a counterexample that would have failed before it. A clean run is not the goal; detecting and preventing repeatable drift is.

Moving the runner to dev-server-1 is separate work. It requires path and CLI checks there, a new unattended signing probe, lane ownership and conflict review, and another independent activation review. No second-machine coordinator is included here.

## Closed product file scopes

Every new config requires `scopes` with exactly the allowlisted item keys. Each scope has exactly `paths` (exact repo-relative files) and `directories` (explicit repo-relative prefixes ending in `/`), with at least one entry overall. For example, a bounded synthetic item can use:

```json
{
  "scopes": {
    "#44": {
      "paths": ["packages/core/src/content/model.ts"],
      "directories": ["apps/web/src/lib/blocks/"]
    }
  }
}
```

This is format documentation, not a current product authorization. Copy the historical `pilot.example.json` to a private config and add the independently reviewed, published item scopes before using it; the historical example deliberately fails the new missing-scope gate. Exact paths and directory prefixes are literal data. Globs, regex syntax, absolute paths, backslashes, control characters, traversal, empty components and blanket root prefixes are refused. Runner files under `tools/handoff-pilot/`, Git metadata, agent instructions and `docs/plans` authority cannot be admitted as product paths. Ordinary handoff/claim/review publication still happens in the separate planning repo under the existing planning checks, including the dev-handoff prohibition.

`dry-run`, `preflight` and `start` validate the same contract. Dry-run reports the scopes and `configDigest`, the SHA-256 of `JSON.stringify` of the parsed complete config. Preflight retains that digest. Independent activation must publish the complete parsed config as a `reference/*.json` file in planning, referenced by `configRecord` in `activation.json` at `planningCommit`. It must also publish that exact `configDigest` in its planning review record and `activation.json`; start checks the published config bytes semantically through the same digest and requires config, preflight and approval digests to agree. Changing scopes or any config field requires fresh published approval and preflight. The four-file runner digest order above is unchanged; all scope implementation lives in its already covered `cli.mjs` and `state.mjs`. No helper is omitted from activation.

Every execute reservation fetches the published main SHA into `codeBase`. The first reservation also fixes the item's `scopeBase` and worktree set; repairs preserve them. After the child returns, the parent fetches the actual PR ref and requires its exact Git object to match GitHub's head. It computes the cumulative item diff from the merge base of that head and current published main, requiring the original item base to remain an ancestor of both. This excludes later independent main changes incorporated into the branch without treating a repair's newer reservation as permission to forget earlier unmerged item changes. It checks both paths of renames/copies, additions and deletions with NUL-delimited Git output, staged and unstaged diffs, and non-ignored untracked paths. New/missing worktrees, an unexpected local HEAD, changed reserved base, unreadable Git evidence or a stale remote PR head fail closed. The same scope is rechecked before review and merge.

A refusal uses the existing terminal blocked/notification route, naming run, item, original base, head, path and reason when available. Private `*-scope-*.json`, binary Git patches and worktree patches retain the evidence; result, state and child logs remain in place. No revert, stash, cleanup, extra repair or counter reset occurs. Historical terminal states remain readable and cannot resume; active legacy states without scopes cannot advance and are never migrated automatically.

This gate checks results and launch transitions. It is not an OS sandbox or tenant isolation and cannot detect temporary changes reverted during a child, ignored build artifacts, arbitrary writes outside the observed checkout, or hostile tampering with the supervisor's own process/state. A shared process and Git repository still require a trusted child, operator observation and the existing stop policy. An admitted net result is not evidence that every intermediate action stayed in scope. R8 requires its own later activation; this change starts no pilot.
